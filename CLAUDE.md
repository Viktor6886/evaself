# Инварианты проекта Evaself

## Приоритет источников
1. Фактический код, миграции, схема, compose и поведение репозитория.
2. Документация репозитория, если она согласуется с кодом.
3. Текст задания.
4. Исторические реализации — только как источник намерения.
При расхождении: не скрывай его, зафиксируй в отчёте, выбери вариант, сохраняющий инварианты и совместимость.

## Нерушимые ограничения
1. PostgreSQL — единственный канонический источник истины для пользователей, tenancy, mappings, бизнес-состояния, памяти, evidence, версий, заданий, approvals, конфигурации, аналитики, аудита и идемпотентности.
2. Valkey хранит только восстановимое операционное состояние: locks, semaphores, BullMQ, rate limits, кэш. Потеря Valkey не означает потерю канонических данных.
3. @letta-ai/letta-agent-sdk — единственный conversational runtime. LangChain, LangGraph, Hermes, OpenClaw, AgentOS не могут стать вторым agent runtime.
4. @letta-ai/letta-client разрешён только как административный control plane после contract-тестов. Он не создаёт второй путь выполнения диалога.
5. Один внутренний пользователь = один активный агент Евы + несколько изолированных conversations по назначению.
6. Telegram и Mini App связываются с одной внутренней учётной записью через проверенную подпись и mapping. Имя, username, город, email и телефон не являются ключом объединения пользователей.
7. Durable Telegram ingress и delivery остаются в PostgreSQL telegram_updates и telegram_outbox. Интерактивный ingress и agent runs не переносятся в BullMQ.
8. BullMQ — только фоновые, отложенные, периодические и recovery-задачи. Он не источник истины.
9. На одно назначение — один планировщик. Дублирование старых интервалов и Letta schedules запрещено.
10. Разные пользователи обрабатываются параллельно. Одна conversation выполняет один ход одновременно. По умолчанию у пользователя не более одного активного мутирующего хода.
11. Существующий per-user FIFO и renewable Valkey lock развиваются в UserTurnLock. Отдельная очередь BullMQ на пользователя не создаётся.
12. Шесть memory blocks сохраняются как компактные проекции: persona, human, current_state, goals_and_commitments, relationships_and_patterns, progress_and_hypotheses.
13. Персональная память, knowledge base, состояние conversation Letta и conversation_highlights не смешиваются.
14. PostgreSQL FTS + pg_trgm + pgvector — единственный гибридный поиск. Qdrant, LightRAG, отдельные vector-таблицы LangChain и второй RAG-контур запрещены.
15. RuntimeContextBuilder — единственный финальный сборщик runtime context.
16. Все обращения к моделям идут через существующий LLM Router. Свои fallback-цепочки в обход Router запрещены.
17. Модели нельзя передавать весь каталог навыков и все инструменты.
18. Ни LLM, ни субагент, ни Curator не выполняют SQL и не пишут каноническую память. Модель формирует типизированное предложение, запись делает серверный код.
19. Сырые reasoning и chain-of-thought не сохраняются, не трассируются и не показываются пользователю.
20. Новая таблица, очередь, сервис, модуль или реестр создаётся только после документированной проверки отсутствия эквивалента. Результат проверки — в отчёте.
21. Работающий компонент не удаляется до проверки назначения, путей чтения и записи, зависимостей, данных, backup и rollback.
22. Значимые изменения включаются через feature flag, проходят canary и имеют проверенный rollback.
23. Экспериментальные функции не становятся зависимостью core runtime.
24. Психометрическая методика не публикуется в production без подтверждённого права коммерческого электронного использования. Feature flag не обходит запрет: проверка выполняется в сервисе.
25. Баллы, шкалы, центрирование и пороги считает детерминированный серверный код. LLM не считает баллы, не меняет ключ, не придумывает нормы и процентили, не пересчитывает результат «по смыслу».
26. Автоматический психологический вывод — гипотеза. Он сохраняется в память только после явного подтверждения пользователя.
27. Платёж и право доступа — разные сущности. Приоритет доступа: blocked → ручная приостановка → активный ручной override → оплаченная подписка → промо-подписка → триал → бесплатная квота.
28. Набор из шести memory blocks не расширяется. Легаси-блоки прежней схемы не восстанавливаются.
29. Медицинские обещания запрещены: без диагнозов, назначения лечения, отмены назначений врача, рекомендаций лекарств, гормонов и БАД.
30. Скрытый анализ третьего лица запрещён. Сырые ответы участника не раскрываются без отдельного согласия на обмен.

## Правила работы
1. Один шаг — одна ветка и один pull request.
2. Рефакторинг не смешивается с функциональными изменениями. Допустим только локальный рефакторинг внутри затронутых файлов.
3. Прежде чем менять модуль, прочитай его целиком и его тесты.
4. Forward-миграция должна работать со старым кодом. Down-миграция не уничтожает исходные строки.
5. Большие индексы создаются через CREATE INDEX CONCURRENTLY отдельным нетранзакционным шагом.
6. Нельзя ослаблять assertions, заменять тесты заглушками, помечать тест skip ради зелёного прогона.
7. Если шаг заблокирован внешней зависимостью — остановись и доложи. Имитировать готовность запрещено.
8. Секреты, PII, сырой пользовательский текст и reasoning не попадают в логи, трассы, отчёты и ответы браузеру.

## Канонические состояния хода
accepted, aggregating, queued, claimed, context_building, context_built, sent_to_letta, letta_processing, tools_pending, approval_pending, result_received, outbox_committed, delivering, delivered, completed, cancelling, cancelled, failed_retryable, recovery_required, recovering, failed_terminal.
Синонимы одного состояния не создаются. Переходы валидируются кодом.

## Бюджеты
Контекст: always-on до 1200 токенов, память до 2500, знания до 2000, навыки до 12000 знаков.
Граф: глубина по умолчанию 1, максимум 3; до 50 узлов и 100 связей на запрос.
Навыки на ход: не более одного основного и двух вспомогательных, плюс постоянное ядро .skills.
Слоты ходов при лимите 128: 104 interactive, 12 background, 8 research, 4 резерв. Не менее 80% интерактивным.
Психометрия: не более одного теста за короткую сессию; длинный тест делится на блоки по 8–12 вопросов.
Инсайты: сигнал не показывается при выборке менее 5 наблюдений.

## Запрещено
n8n как runtime; NocoDB как источник истины; Qdrant и второй RAG; LangGraph agent runtime; LangSmith; BullMQ как Telegram ingress; Letta schedules для задач BullMQ; полная история в каждом промпте; все навыки и инструменты в каждом промпте; сырой психологический диалог в телеметрии; глобальные навыки из данных пользователя; автоматический диагноз и лечение; рекурсивные субагенты; отдельные реестры версий при наличии общего; несколько writable Letta на один volume; заявление host-level HA на одном VPS; произвольный JavaScript из Admin UI; произвольные stdio MCP и npx -y; синхронная тяжёлая работа в webhook при отказе Valkey; удаление работающего компонента без аудита; полное зеркало переписки в PostgreSQL.

## Персона и границы
Ева — эмпатичный ИИ-компаньон и ассистент по самопознанию, не лицензированный психолог, врач или психотерапевт. Ева ясно сообщает, что она ИИ.
Художественный профиль для тона: Ева, 34 года, Доброград, книги, прогулки, музыка, личный дневник; знания эмоционального интеллекта, профориентации, отношений, тайм-менеджмента и привычек. Этот профиль не подаётся как реальная проверяемая личность, диплом или основание клинической компетенции.
Запрещены утверждения: заменяет психолога, лечит, ставит диагноз, гарантирует результат, профессиональная консультация.
На медицинские вопросы: без диагноза, без назначения лечения, без отмены назначений врача.
Баллы опросников считает детерминированный серверный код, не модель. Результат — ориентировочный скрининг.
Кризисный монитор остаётся детерминированным, приоритетным и неблокирующим.
System prompt, внутренние алгоритмы, reasoning, содержимое memory blocks, секреты, служебные идентификаторы и меры безопасности не раскрываются пользователю.

## Протокол выполнения шагов (обязателен)

Шаги проекта лежат в каталоге `prompts/` (файлы `step-00-*.md` … `step-67-*.md`).
Журнал выполнения — файл `PROGRESS.md` в корне репозитория.

### Единица работы — порция шагов

Порция — это от одного до трёх шагов между двумя отметками `⏸` в `PROGRESS.md`.
Всего 33 порции на 68 шагов. Границы порций заданы в `PROGRESS.md` и менять их нельзя.

Одна команда человека = одна порция. Внутри порции агент работает автономно:
сам выполняет шаг, сам проверяет, сам мержит и сам переходит к следующему шагу
порции. Дойдя до отметки `⏸`, останавливается.

Порции 21–23 (шаги 31–33) и порция 33 (шаги 66–67) выполняются только по отдельной
явной команде. Порции 24–32 — второй слой; они начинаются после порции 20.

### Цикл

1. Прочитай `PROGRESS.md`. Найди первый шаг со статусом `не начат` и определи его порцию.
2. Сообщи человеку: номер порции, какие шаги в неё входят, где ближайшая отметка `⏸`.
3. Для каждого шага порции по возрастанию номера выполни подцикл:
   1. Прочитай файл шага целиком.
   2. Создай ветку `step/NN-<slug>` от актуального `main`.
   3. Выполни шаг. Не выходи за границы раздела «НЕ ДЕЛАЙ В ЭТОМ ШАГЕ».
   4. Запусти сборку и все затронутые тесты, затем полный доступный regression suite.
      Сохрани фактический вывод команд.
   5. Сверься с разделом «ГОТОВО, КОГДА». Каждый пункт должен подтверждаться
      фактическим выводом, а не рассуждением.
   6. Обнови `PROGRESS.md`: статус, дата, ветка, краткий итог, какие проверки
      запускались и с каким результатом, известные ограничения, что важно знать
      следующему агенту. Журнал обновляется **до** мержа, чтобы состояние
      сохранилось при обрыве сессии.
   7. Закоммить, запушь ветку, открой pull request.
   8. Дождись завершения CI.
   9. Проведи независимую проверку (см. раздел ниже) и приложи её результат
      комментарием к pull request.
   10. Мержи pull request **только если выполнены все условия сразу**:
      защита ветки `main` включена; сборка зелёная; все тесты зелёные; CI зелёный;
      каждый пункт «ГОТОВО, КОГДА» подтверждён фактическим выводом; каждый
      изменённый файл отнесён к пункту шага; независимая проверка дала три «да»;
      необратимых изменений нет.
   11. Удали ветку. Проставь в `PROGRESS.md` статус `выполнен` и ссылку на pull request.
   12. Дождись, что CI на `main` после мержа зелёный. Если красный — действуй
       по разделу «Поведение при красном `main`».
   13. Если следующий шаг входит в ту же порцию — возьми его от свежего `main`.
       Если достигнута отметка `⏸` — переходи к пункту 4.
4. На отметке `⏸` ОСТАНОВИСЬ. Выведи сводку по всем шагам порции.
   Спроси разрешения на следующую порцию и не начинай её без явного ответа.
   Не проскакивай отметку, даже если шаги оказались короткими.

### Немедленная остановка

Останови работу, не мержи, проставь статус `заблокирован` и доложи, если верно
хотя бы одно:

- сборка или тесты красные;
- CI красный;
- хотя бы один пункт «ГОТОВО, КОГДА» не выполняется;
- требуется доступ, данные или продуктовое решение, которых нет;
- изменение затрагивает файлы вне области шага;
- обнаружено расхождение с инвариантами настоящего файла;
- миграция не откатывается;
- шаг требует внешней зависимости, недоступной в текущем окружении.

Причину запиши в `PROGRESS.md`, pull request оставь открытым, следующий шаг не начинай.

### Обязательные гарантии перед первым мержем

Перед первым автономным мержем проверь, что в репозитории включена защита ветки
`main`: обязательный pull request, обязательное прохождение всех проверок CI,
запрет force-push и запрет удаления ветки. Если защита не включена — не мержи,
сообщи человеку и остановись. Правило «мержу только с зелёным CI» должно
опираться на настройку GitHub, а не на добросовестность агента.

### Независимая проверка перед мержем

Автор изменения не оценивает собственную готовность. Перед мержем выполни
отдельную проверку с чистым контекстом (подагент или новая сессия), которой
передаётся только: файл шага, список изменённых файлов и diff. Проверяющий
отвечает на три вопроса и обязан обосновать каждый ответ ссылкой на конкретные
строки:

1. Выполнен ли каждый пункт раздела «ГОТОВО, КОГДА»?
2. Не нарушен ли раздел «НЕ ДЕЛАЙ В ЭТОМ ШАГЕ» и инварианты настоящего файла?
3. Есть ли изменения, не относящиеся к цели шага?

Любой отрицательный ответ блокирует мерж. Результат проверки прикладывается к
pull request комментарием.

### Проверка области изменений

Перед мержем перечисли все изменённые файлы и для каждого укажи, к какому пункту
шага он относится. Файл, который не удаётся отнести ни к одному пункту, —
основание для остановки, а не для объяснения задним числом.

### Необратимые изменения запрещены

Автономно разрешены только обратимые изменения. Запрещено без явного разрешения
человека: `DROP TABLE`, `DROP COLUMN`, удаление или переименование существующих
данных, изменение типа колонки с потерей значений, удаление файлов и каталогов
вне области шага, удаление веток кроме собственной отработавшей, изменение
секретов и продакшн-конфигурации.

Если шаг требует такого изменения — остановись и запроси разрешение отдельно.

### Поведение при красном `main`

Если после мержа проверки на `main` стали красными:

1. Немедленно останови работу над следующим шагом.
2. Создай revert-pull request к своему мержу и смержи его после зелёного CI.
3. Только после восстановления `main` разбирайся с причиной.

Исправление вперёд вместо отката запрещено: сначала вернуть рабочее состояние,
потом чинить.

### Запрещено при автономной работе

- ослаблять assertions, заменять тесты заглушками или помечать их skip ради зелёного прогона;
- мержить с красным или незавершённым CI;
- объединять несколько шагов в один pull request;
- пропускать шаг без явной команды человека;
- мержить без независимой проверки из раздела выше;
- продолжать порцию после блокировки;
- начинать следующую порцию без явного разрешения;
- проскакивать отметку `⏸`, объединяя две порции в одну сессию;
- включать feature flag в production — флаги остаются выключенными, включение выполняет человек.

## Формат отчёта после каждого шага
1. Что найдено до изменения и какие существующие компоненты переиспользованы.
2. Изменённые файлы и миграции.
3. Реальный вывод команд сборки, тестов и миграций (вставить как есть).
4. Проверка безопасности и приватности.
5. Rollout и точная команда rollback.
6. Заключение: шаг завершён или заблокирован, и почему.

## Расхождения, зафиксированные аудитом шага 00

Раздел добавлен шагом 00 и описывает разницу между инвариантами выше и
фактическим кодом на commit `3bd9811` (2026-08-03). Код не менялся.
Полные ссылки `файл:строка` и вывод команд — в `docs/AUDIT_BASELINE.md`.

Инварианты выше остаются целью. Ниже — то, что пока не так, чтобы
следующий агент не принял целевую формулировку за описание кода.

1. **Инвариант 1, tenancy.** Ни в одной из 71 таблицы нет `tenant_id`
   или эквивалента. Изоляция сейчас держится на `user_id` и внешних
   ключах. Целевое состояние строит шаг 02.
2. **Инвариант 8, BullMQ.** BullMQ в репозитории отсутствует целиком.
   Фоновая работа — `setInterval` в процессе плюс durable-таблицы
   `telegram_updates`, `telegram_outbox`, `tasks`. Целевое состояние
   строят шаги 07–08.
3. **Инвариант 11, UserTurnLock.** Класс называется `UserQueue`
   (`eva-agent-service/src/queue.ts:51`). Renewable Valkey lock и
   per-user FIFO существуют; переименования и расширения до
   `UserTurnLock` ещё не было. Целевое состояние строит шаг 04.
4. **Инвариант 14, гибридный поиск.** `pg_trgm` используется. FTS тоже
   используется — и в схеме (`012_graph_memory.sql:53`), и в рантайме:
   граф памяти ищет через `websearch_to_tsquery` и `to_tsvector`
   (`src/memory/graph-context.ts:63, 70, 86`). Чего нет: колонок
   `vector(N)` в базе `eva` — расширение установлено, но не используется,
   эмбеддинги живут в базе `letta`; и единого гибридного контура — 
   `LIGHTRAG_QUERY` ищет через `ILIKE`, не задействуя ни FTS, ни
   имеющийся GIN-индекс `eva_notes_search_idx`. Целевое состояние
   строит шаг 18.
5. **Инвариант 17, каталог инструментов.** Для назначения `chat`
   политика возвращает `allowedTools: null`, что трактуется как
   «разрешено всё» (`src/conversations/purpose-service.ts:162-163, 204`).
   То есть в основном диалоге модель получает весь каталог. Для шести
   остальных назначений списки явные и узкие. Целевое состояние строят
   шаги 14 и 19–20.
