# Инварианты и протокол проекта Evaself

Этот файл читается целиком в каждой сессии. В нём только то, что нужно всегда:
инварианты, безопасность, бюджеты, batch-протокол. Всё остальное — по ссылкам,
и читается **только при необходимости**.

| Нужно | Где |
|---|---|
| Где остановилась работа | `PROGRESS.md` |
| Что уже реализовано и что переиспользовать | `docs/IMPLEMENTATION_STATE.md` |
| Чем код отличается от инвариантов | `docs/INVARIANT_DIVERGENCES.md` |
| Разбор уже сделанного шага | `docs/PROGRESS_HISTORY.md` |
| Задание шага | `prompts/step-NN-*.md` |
| Тон, персона, тексты пользователю | `docs/PERSONA.md` |
| Правила подсистемы | локальный `CLAUDE.md` внутри её каталога |

## Приоритет источников

1. Фактический код, миграции, схема, compose и поведение репозитория.
2. Документация репозитория, если она согласуется с кодом.
3. Текст задания.
4. Исторические реализации — только как источник намерения.

При расхождении: не скрывай его, зафиксируй в отчёте, выбери вариант,
сохраняющий инварианты и совместимость.

## Нерушимые ограничения

1. PostgreSQL — единственный канонический источник истины для пользователей, tenancy, mappings, бизнес-состояния, памяти, evidence, версий, заданий, approvals, конфигурации, аналитики, аудита и идемпотентности.
2. Valkey хранит только восстановимое операционное состояние: locks, semaphores, BullMQ, rate limits, кэш. Потеря Valkey не означает потерю канонических данных.
3. @letta-ai/letta-agent-sdk — единственный conversational runtime. LangChain, LangGraph, Hermes, OpenClaw, AgentOS не могут стать вторым agent runtime.
4. @letta-ai/letta-client разрешён только как административный control plane после contract-тестов. Он не создаёт второй путь выполнения диалога.
5. Один внутренний пользователь = один активный агент Евы + несколько изолированных conversations по назначению.
6. Telegram и Mini App связываются с одной внутренней учётной записью через проверенную подпись и mapping. Имя, username, город, email и телефон не являются ключом объединения пользователей.
7. Durable Telegram ingress и delivery остаются в PostgreSQL `telegram_updates` и `telegram_outbox`. Интерактивный ingress и agent runs не переносятся в BullMQ.
8. BullMQ — только фоновые, отложенные, периодические и recovery-задачи. Он не источник истины.
9. На одно назначение — один планировщик. Дублирование старых интервалов и Letta schedules запрещено.
10. Разные пользователи обрабатываются параллельно. Одна conversation выполняет один ход одновременно. По умолчанию у пользователя не более одного активного мутирующего хода.
11. Существующий per-user FIFO и renewable Valkey lock развиваются в UserTurnLock. Отдельная очередь BullMQ на пользователя не создаётся.
12. Шесть memory blocks сохраняются как компактные проекции: `persona`, `human`, `current_state`, `goals_and_commitments`, `relationships_and_patterns`, `progress_and_hypotheses`.
13. Персональная память, knowledge base, состояние conversation Letta и `conversation_highlights` не смешиваются.
14. PostgreSQL FTS + pg_trgm + pgvector — единственный гибридный поиск. Qdrant, LightRAG, отдельные vector-таблицы LangChain и второй RAG-контур запрещены.
15. RuntimeContextBuilder — единственный финальный сборщик runtime context.
16. Все обращения к моделям идут через существующий LLM Router. Свои fallback-цепочки в обход Router запрещены.
17. Модели нельзя передавать весь каталог навыков и все инструменты.
18. Ни LLM, ни субагент, ни Curator не выполняют SQL и не пишут каноническую память. Модель формирует типизированное предложение, запись делает серверный код.
19. Сырые reasoning и chain-of-thought не сохраняются, не трассируются и не показываются пользователю.
20. Новая таблица, очередь, сервис, модуль или реестр создаётся только после документированной проверки отсутствия эквивалента. Результат проверки — в отчёте.
21. Работающий компонент не удаляется до проверки назначения, путей чтения и записи, зависимостей, данных, backup и rollback.
22. Значимые изменения включаются через feature flag, проходят canary и имеют проверенный rollback.
23. Экспериментальные функции не становятся зависимостью core runtime.
24. Психометрическая методика не публикуется в production без подтверждённого права коммерческого электронного использования. Feature flag не обходит запрет: проверка выполняется в сервисе.
25. Баллы, шкалы, центрирование и пороги считает детерминированный серверный код. LLM не считает баллы, не меняет ключ, не придумывает нормы и процентили, не пересчитывает результат «по смыслу».
26. Автоматический психологический вывод — гипотеза. Он сохраняется в память только после явного подтверждения пользователя.
27. Платёж и право доступа — разные сущности. Приоритет доступа: blocked → ручная приостановка → активный ручной override → оплаченная подписка → промо-подписка → триал → бесплатная квота.
28. Набор из шести memory blocks не расширяется. Легаси-блоки прежней схемы не восстанавливаются.
29. Медицинские обещания запрещены: без диагнозов, назначения лечения, отмены назначений врача, рекомендаций лекарств, гормонов и БАД.
30. Скрытый анализ третьего лица запрещён. Сырые ответы участника не раскрываются без отдельного согласия на обмен.

Чем фактический код сегодня отличается от этих формулировок —
`docs/INVARIANT_DIVERGENCES.md`.

## Запрещено

n8n как runtime; NocoDB как источник истины; Qdrant и второй RAG; LangGraph
agent runtime; LangSmith; BullMQ как Telegram ingress; Letta schedules для задач
BullMQ; полная история в каждом промпте; все навыки и инструменты в каждом
промпте; сырой психологический диалог в телеметрии; глобальные навыки из данных
пользователя; автоматический диагноз и лечение; рекурсивные субагенты; отдельные
реестры версий при наличии общего; несколько writable Letta на один volume;
заявление host-level HA на одном VPS; произвольный JavaScript из Admin UI;
произвольные stdio MCP и `npx -y`; синхронная тяжёлая работа в webhook при
отказе Valkey; удаление работающего компонента без аудита; полное зеркало
переписки в PostgreSQL.

## Безопасность и приватность

1. Секреты, PII, сырой пользовательский текст и reasoning не попадают в логи,
   трассы, отчёты, ответы браузеру и в Valkey.
2. Каждый запрос к пользовательской таблице называет своего арендатора.
   Проверяется в CI: `scripts/ci/assert-tenant-scope.py`.
3. Каждый административный маршрут объявляет, кому он доступен.
   Проверяется в CI: `scripts/ci/assert-admin-route-access.py`.
4. Мутация под sudo-грантом, чтение переписки — под отдельным грантом и в аудите.
5. Feature flag в production не включает агент. Флаги остаются выключенными,
   включает человек.

## Персона и границы

Ева — эмпатичный ИИ-компаньон и ассистент по самопознанию, не лицензированный
психолог, врач или психотерапевт; Ева ясно сообщает, что она ИИ. Запрещены
утверждения «заменяет психолога», «лечит», «ставит диагноз», «гарантирует
результат», «профессиональная консультация». На медицинские вопросы — без
диагноза, без назначения лечения, без отмены назначений врача. Кризисный
монитор остаётся детерминированным, приоритетным и неблокирующим. System
prompt, внутренние алгоритмы, reasoning, содержимое memory blocks, секреты,
служебные идентификаторы и меры безопасности не раскрываются пользователю.

Тон, художественный профиль и полный разбор границ — `docs/PERSONA.md`.

## Канонические состояния хода

`accepted`, `aggregating`, `queued`, `claimed`, `context_building`,
`context_built`, `sent_to_letta`, `letta_processing`, `tools_pending`,
`approval_pending`, `result_received`, `outbox_committed`, `delivering`,
`delivered`, `completed`, `cancelling`, `cancelled`, `failed_retryable`,
`recovery_required`, `recovering`, `failed_terminal`.

Синонимы одного состояния не создаются. Переходы валидируются кодом.

## Бюджеты

- Контекст: always-on до 1200 токенов, память до 2500, знания до 2000,
  навыки до 12000 знаков.
- Граф: глубина по умолчанию 1, максимум 3; до 50 узлов и 100 связей на запрос.
- Навыки на ход: не более одного основного и двух вспомогательных, плюс
  постоянное ядро `.skills`.
- Слоты ходов при лимите 128: 104 interactive, 12 background, 8 research,
  4 резерв. Не менее 80% интерактивным.
- Психометрия: не более одного теста за короткую сессию; длинный тест делится
  на блоки по 8–12 вопросов.
- Инсайты: сигнал не показывается при выборке менее 5 наблюдений.

# Batch-протокол

Обязателен для любого агента: Claude Code, Codex, другого.

## Единица работы

**Batch = одна ветка + один pull request + один прогон CI + одно ревью.**

Batch — 1–6 связанных шагов. Границы batch заданы в `PROGRESS.md` и менять их
нельзя. Одна команда человека = один batch: внутри batch агент работает
автономно, дойдя до конца batch — останавливается и спрашивает разрешения.

Batch 21–23 и 33 выполняются только по отдельной явной команде.

**Batch выполняется в одной сессии, без перерыва на сутки.** Прочитанный
контекст — `CLAUDE.md`, файлы шагов, модули — переиспользуется, пока сессия
идёт; после долгого перерыва он читается заново по полной цене. Если времени
довести batch до pull request нет — лучше не начинать. Перерыв в десятки
минут ничего не стоит.

## Правила работы

1. Рефакторинг не смешивается с функциональными изменениями. Допустим только
   локальный рефакторинг внутри затронутых файлов.
2. Прежде чем менять модуль, прочитай его целиком и его тесты.
3. Forward-миграция должна работать со старым кодом. Down-миграция не
   уничтожает исходные строки.
4. Большие индексы создаются через `CREATE INDEX CONCURRENTLY` отдельным
   нетранзакционным шагом.
5. Имитировать готовность запрещено: заблокирован — остановись и доложи.

## Что читать

Только по необходимости, без полного ре-скана репозитория:

1. `PROGRESS.md` — где остановились.
2. Файлы шагов текущего batch.
3. `docs/IMPLEMENTATION_STATE.md` — что уже есть и что переиспользовать.
4. Модули, которые batch действительно меняет, — целиком, вместе с их тестами.
5. Локальный `CLAUDE.md` подсистемы, если он есть.

**Целиком читается только модуль, который batch меняет.** Соседний модуль,
из которого нужен один контракт, читается через поиск и чтение нужного
участка, а не полностью: `src/admin/stt-service.ts` — это 1900 строк,
`admin-ui/public/ui.js` — 3350, и каждое их полное чтение стоит десятков
тысяч токенов.

Не читай: `docs/PROGRESS_HISTORY.md`, `docs/AUDIT_BASELINE.md`,
`docs/EVASELF_LAYER2_PLAN.md`, `.docx`, документы соседних подсистем — пока
конкретный вопрос не потребовал. `.docx` не читаются никогда: всё, что в них
есть, разложено по `prompts/`.

## Ответы инструментов ограничиваются на стороне вызова

Ответ, который пришлось усечь, уже оплачен целиком. Любой вызов, способный
вернуть больше экрана, ограничивается заранее:

- команда оболочки — `| tail -20`, `--quiet`, `-q`;
- список через API — `per_page`, `minimal_output: true`;
- логи упавшей job — `failed_only`, `tail_lines`;
- дифф — с исключениями (см. «Ревью»).

Один неограниченный запрос списка прогонов CI возвращает 386 000 символов.
Тот же запрос с `per_page` — две страницы текста.

## Размер файла — это стоимость чтения

Файл больше 600 строк читается дорого и перечитывается в каждой сессии,
которая его касается. Шаг, который такой файл **и так переписывает**, обязан
оставить после себя модули поменьше. Отдельным рефакторингом это делать
нельзя — правило 1 запрещает мешать рефакторинг с функциональными
изменениями.

Сегодня за границей: `admin-ui/public/ui.js` (3350), `src/admin/stt-service.ts`
(1879), `src/server.ts` (1498), `src/letta.ts` (1471), `src/db.ts` (1159),
`src/admin/server.ts` (1092), `src/public/webapp-core.ts` (1070),
`src/eva-workflow.ts` (973), `src/router/router.ts` (928).

## Цикл batch

**Открытие (один раз на batch).**

1. Прочитай `PROGRESS.md`. Определи batch: номер, шаги, статус.
2. Прочитай все файлы шагов batch и `docs/IMPLEMENTATION_STATE.md`.
3. Разбери batch один раз: шаги, зависимости между ними, риски, порядок
   выполнения, тест-стратегия. Что переиспользуется, что создаётся впервые.
4. Сообщи человеку: номер batch, шаги, порядок, план проверок.
5. Создай ветку `batch/NN-<slug>` от актуального `main`: `NN` — номер batch,
   `slug` — от первого шага в нём. Если ветка уже есть — возобнови её
   (см. «Возобновление»).

**Шаг (для каждого шага batch по возрастанию номера).**

6. Реализация. Не выходи за границы раздела «НЕ ДЕЛАЙ В ЭТОМ ШАГЕ».
7. Targeted tests — только тесты, затронутые шагом. Full regression здесь
   не запускается.
8. Сверься с разделом «ГОТОВО, КОГДА». Каждый пункт подтверждается фактическим
   результатом команды, а не рассуждением.
9. Checkpoint: commit → обнови блок состояния в `PROGRESS.md` → push.
   Checkpoint-push полный CI не запускает.
10. Следующий шаг batch.

**Закрытие batch.**

11. Full regression: сборка, линт, типы, все тесты затронутых сервисов.
12. Перечисли все изменённые файлы и отнеси каждый к пункту задания. Файл,
    который не относится ни к одному пункту, — основание для остановки, а не
    для объяснения задним числом.
13. Обнови `PROGRESS.md` (статус batch, PR) и добавь запись в
    `docs/PROGRESS_HISTORY.md`. Обнови `docs/IMPLEMENTATION_STATE.md`, если
    появился новый компонент или изменился контракт существующего.
14. Открой pull request на весь batch. Дождись зелёного CI **одним ожиданием**:
    полный прогон занимает около восьми минут, опрос каждые полминуты — это
    пятнадцать оплаченных ответов вместо одного.
15. Независимое ревью — одно на batch, по накопленному diff (см. ниже).
    Результат приложи комментарием к pull request.
16. Мержи только если выполнены все условия сразу: защита ветки `main`
    включена; CI зелёный; каждый пункт «ГОТОВО, КОГДА» каждого шага
    подтверждён; каждый изменённый файл отнесён к пункту; ревью дало три «да»;
    необратимых изменений нет.
17. Удали ветку. Проставь в `PROGRESS.md` статус `выполнен` и ссылку на PR.
18. Дождись зелёного CI на `main`. Если красный — раздел «Красный `main`».
19. Остановись. Выведи сводку по batch и спроси разрешения на следующий.

## Проверки

- **После шага** — только targeted tests: тесты изменённых модулей плюс те,
  что зависят от изменённого контракта. Команды подсистемы — в её локальном
  `CLAUDE.md`.
- **В конце batch** — full regression по всем затронутым сервисам.
- **CI** — полный прогон только на pull request, на `main` и по ручному
  запуску. Checkpoint-пуши в ветку batch его не запускают.
- Дорогие job (`images`, `stack`, браузерные тесты `admin-ui`, тесты
  `media-service`) внутри себя пропускают шаги, которым при этом изменении
  нечего проверять — правила в `scripts/ci/changed-scope.sh`. Job при этом
  всё равно выполняется и отдаёт `success`: пропущенная job не засчитывается
  обязательной проверкой в защите ветки.

## Логи

Не сохраняй большой stdout — ни в отчёте, ни в `PROGRESS.md`, ни в
`docs/PROGRESS_HISTORY.md`. Формат записи о проверке:

```
npm test → PASS
python3 scripts/ci/assert-tenant-scope.py → PASS
node --test test/turn-lifecycle.test.ts → FAIL (3 из 41)
```

Полный вывод приводится только для FAIL и только той части, что объясняет
отказ. Вывод зелёного прогона не пересказывается и не цитируется.

## Ревью

Одно независимое ревью на batch, по накопленному diff, с чистым контекстом
(подагент или новая сессия). Автор изменения не оценивает собственную
готовность.

Дифф для ревью берётся без сгенерированных файлов — ревьюер не извлечёт из
них ничего, а полторы тысячи строк `package-lock.json` прочитает:

```
git diff main... -- . \
  ':(exclude)**/package-lock.json' \
  ':(exclude)docs/PROGRESS_HISTORY.md'
```

Ревью выполняется на модели попроще, чем реализация (Sonnet): вопросов три,
они фиксированные, и ответ на каждый обоснован ссылкой на строки — задача не
требует модели уровня реализации. Реализация остаётся на основной модели.

Проверяющему передаётся только: файлы шагов batch, список изменённых файлов
и дифф. Три вопроса, каждый ответ обоснован ссылкой на конкретные строки:

1. Выполнен ли каждый пункт раздела «ГОТОВО, КОГДА» каждого шага batch?
2. Не нарушен ли раздел «НЕ ДЕЛАЙ В ЭТОМ ШАГЕ» и инварианты этого файла?
3. Есть ли изменения, не относящиеся к целям шагов batch?

Любой отрицательный ответ блокирует мерж.

## Возобновление

Состояние восстанавливается из Git и `PROGRESS.md`, а не из памяти сессии.
После обрыва:

1. `git fetch origin && git checkout <BRANCH>` из блока состояния.
2. Сверь `LAST_COMMIT` с `git log -1`. Расхождение означает незакоммиченную
   работу — она потеряна, шаг переделывается с последнего checkpoint.
3. Продолжи с `CURRENT_STEP` и `NEXT`.

Поэтому блок состояния обновляется **до** пуша, а не после.

## Немедленная остановка

Останови работу, не мержи, проставь `STATUS: заблокирован`, заполни `BLOCKER`
и доложи, если верно хотя бы одно:

- сборка, тесты или CI красные;
- хотя бы один пункт «ГОТОВО, КОГДА» не выполняется;
- требуется доступ, данные или продуктовое решение, которых нет;
- изменение затрагивает файлы вне области batch;
- обнаружено расхождение с инвариантами этого файла;
- миграция не откатывается;
- шаг требует внешней зависимости, недоступной в окружении.

Pull request оставь открытым, следующий batch не начинай.

## Необратимые изменения запрещены

Автономно разрешены только обратимые изменения. Без явного разрешения человека
запрещено: `DROP TABLE`, `DROP COLUMN`, удаление или переименование
существующих данных, изменение типа колонки с потерей значений, удаление файлов
и каталогов вне области batch, удаление веток кроме собственной отработавшей,
изменение секретов и продакшн-конфигурации.

Если шаг требует такого изменения — остановись и запроси разрешение отдельно.

## Красный `main`

1. Немедленно останови работу над следующим batch.
2. Создай revert-pull request к своему мержу и смержи его после зелёного CI.
3. Только после восстановления `main` разбирайся с причиной.

Исправление вперёд вместо отката запрещено.

## Перед первым мержем

Проверь, что на `main` включена защита: обязательный pull request, обязательное
прохождение проверок CI, запрет force-push, запрет удаления ветки. Если защита
не включена — не мержи, сообщи человеку и остановись.

## Запрещено при автономной работе

- ослаблять assertions, заменять тесты заглушками, помечать их `skip`;
- мержить с красным или незавершённым CI;
- мержить без независимого ревью;
- разбивать batch на несколько pull request или объединять два batch в один;
- пропускать шаг без явной команды человека;
- продолжать batch после блокировки;
- начинать следующий batch без явного разрешения;
- включать feature flag в production.

## Отчёт после batch

Один отчёт на batch, коротко:

1. Что переиспользовано из существующего и что создано впервые (по каждому шагу).
2. Изменённые файлы и миграции — списком, с привязкой к пунктам задания.
3. Проверки в формате `команда → PASS/FAIL`. Полный вывод — только для FAIL.
4. Проверка безопасности и приватности: тенантность, секреты, логи, PII.
5. Rollout и точная команда rollback.
6. Заключение: batch завершён или заблокирован, и почему.
