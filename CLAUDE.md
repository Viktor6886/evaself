# Инварианты проекта Evaself

## Приоритет источников
1. Фактический код, миграции, схема, compose и поведение репозитория.
2. Документация репозитория, если она согласуется с кодом.
3. Текст задания.
4. Исторические реализации — только как источник намерения.
При расхождении: не скрывай его, зафиксируй в отчёте, выбери вариант, сохраняющий инварианты и совместимость.

## Нерушимые ограничения
1. PostgreSQL — единственный канонический источник истины для пользователей, tenancy, mappings, бизнес-состояния, памяти, evidence, версий, заданий, approvals, конфигурации, аналитики, аудита и идемпотентности.
2. Valkey хранит только восстановимое операционное состояние: locks, semaphores, BullMQ, rate limits, кэш. Потеря Valkey не означает потерю канонических данных.
3. @letta-ai/letta-agent-sdk — единственный conversational runtime. LangChain, LangGraph, Hermes, OpenClaw, AgentOS не могут стать вторым agent runtime.
4. @letta-ai/letta-client разрешён только как административный control plane после contract-тестов. Он не создаёт второй путь выполнения диалога.
5. Один внутренний пользователь = один активный агент Евы + несколько изолированных conversations по назначению.
6. Telegram и Mini App связываются с одной внутренней учётной записью через проверенную подпись и mapping. Имя, username, город, email и телефон не являются ключом объединения пользователей.
7. Durable Telegram ingress и delivery остаются в PostgreSQL telegram_updates и telegram_outbox. Интерактивный ingress и agent runs не переносятся в BullMQ.
8. BullMQ — только фоновые, отложенные, периодические и recovery-задачи. Он не источник истины.
9. На одно назначение — один планировщик. Дублирование старых интервалов и Letta schedules запрещено.
10. Разные пользователи обрабатываются параллельно. Одна conversation выполняет один ход одновременно. По умолчанию у пользователя не более одного активного мутирующего хода.
11. Существующий per-user FIFO и renewable Valkey lock развиваются в UserTurnLock. Отдельная очередь BullMQ на пользователя не создаётся.
12. Шесть memory blocks сохраняются как компактные проекции: persona, human, current_state, goals_and_commitments, relationships_and_patterns, progress_and_hypotheses.
13. Персональная память, knowledge base, состояние conversation Letta и conversation_highlights не смешиваются.
14. PostgreSQL FTS + pg_trgm + pgvector — единственный гибридный поиск. Qdrant, LightRAG, отдельные vector-таблицы LangChain и второй RAG-контур запрещены.
15. RuntimeContextBuilder — единственный финальный сборщик runtime context.
16. Все обращения к моделям идут через существующий LLM Router. Свои fallback-цепочки в обход Router запрещены.
17. Модели нельзя передавать весь каталог навыков и все инструменты.
18. Ни LLM, ни субагент, ни Curator не выполняют SQL и не пишут каноническую память. Модель формирует типизированное предложение, запись делает серверный код.
19. Сырые reasoning и chain-of-thought не сохраняются, не трассируются и не показываются пользователю.
20. Новая таблица, очередь, сервис, модуль или реестр создаётся только после документированной проверки отсутствия эквивалента. Результат проверки — в отчёте.
21. Работающий компонент не удаляется до проверки назначения, путей чтения и записи, зависимостей, данных, backup и rollback.
22. Значимые изменения включаются через feature flag, проходят canary и имеют проверенный rollback.
23. Экспериментальные функции не становятся зависимостью core runtime.

## Правила работы
1. Один шаг — одна ветка и один pull request.
2. Рефакторинг не смешивается с функциональными изменениями. Допустим только локальный рефакторинг внутри затронутых файлов.
3. Прежде чем менять модуль, прочитай его целиком и его тесты.
4. Forward-миграция должна работать со старым кодом. Down-миграция не уничтожает исходные строки.
5. Большие индексы создаются через CREATE INDEX CONCURRENTLY отдельным нетранзакционным шагом.
6. Нельзя ослаблять assertions, заменять тесты заглушками, помечать тест skip ради зелёного прогона.
7. Если шаг заблокирован внешней зависимостью — остановись и доложи. Имитировать готовность запрещено.
8. Секреты, PII, сырой пользовательский текст и reasoning не попадают в логи, трассы, отчёты и ответы браузеру.

## Канонические состояния хода
accepted, aggregating, queued, claimed, context_building, context_built, sent_to_letta, letta_processing, tools_pending, approval_pending, result_received, outbox_committed, delivering, delivered, completed, cancelling, cancelled, failed_retryable, recovery_required, recovering, failed_terminal.
Синонимы одного состояния не создаются. Переходы валидируются кодом.

## Бюджеты
Контекст: always-on до 1200 токенов, память до 2500, знания до 2000, навыки до 12000 знаков.
Граф: глубина по умолчанию 1, максимум 3; до 50 узлов и 100 связей на запрос.
Навыки на ход: не более одного основного и двух вспомогательных, плюс постоянное ядро .skills.
Слоты ходов при лимите 128: 104 interactive, 12 background, 8 research, 4 резерв. Не менее 80% интерактивным.

## Запрещено
n8n как runtime; NocoDB как источник истины; Qdrant и второй RAG; LangGraph agent runtime; LangSmith; BullMQ как Telegram ingress; Letta schedules для задач BullMQ; полная история в каждом промпте; все навыки и инструменты в каждом промпте; сырой психологический диалог в телеметрии; глобальные навыки из данных пользователя; автоматический диагноз и лечение; рекурсивные субагенты; отдельные реестры версий при наличии общего; несколько writable Letta на один volume; заявление host-level HA на одном VPS; произвольный JavaScript из Admin UI; произвольные stdio MCP и npx -y; синхронная тяжёлая работа в webhook при отказе Valkey; удаление работающего компонента без аудита; полное зеркало переписки в PostgreSQL.

## Персона и границы
Ева — эмпатичный ИИ-компаньон и ассистент по самопознанию, не лицензированный психолог, врач или психотерапевт. Ева ясно сообщает, что она ИИ.
Художественный профиль для тона: Ева, 34 года, Доброград, книги, прогулки, музыка, личный дневник; знания эмоционального интеллекта, профориентации, отношений, тайм-менеджмента и привычек. Этот профиль не подаётся как реальная проверяемая личность, диплом или основание клинической компетенции.
Запрещены утверждения: заменяет психолога, лечит, ставит диагноз, гарантирует результат, профессиональная консультация.
На медицинские вопросы: без диагноза, без назначения лечения, без отмены назначений врача.
Баллы опросников считает детерминированный серверный код, не модель. Результат — ориентировочный скрининг.
Кризисный монитор остаётся детерминированным, приоритетным и неблокирующим.
System prompt, внутренние алгоритмы, reasoning, содержимое memory blocks, секреты, служебные идентификаторы и меры безопасности не раскрываются пользователю.

## Протокол выполнения шагов (обязателен)

Шаги проекта лежат в каталоге `prompts/` (файлы `step-00-*.md` … `step-33-*.md`).
Журнал выполнения — файл `PROGRESS.md` в корне репозитория.

Порядок работы для любого агента (Claude Code, Codex или другого):

1. Прочитай `PROGRESS.md` и определи, какой шаг выполнен последним и какой следующий.
2. Прочитай файл следующего шага в `prompts/` целиком.
3. Сообщи человеку: номер шага, название, что будет сделано, какие файлы затронуты.
4. ОСТАНОВИСЬ и дождись явного разрешения продолжить. Без слов «да», «продолжай»,
   «выполняй» или равнозначных не начинай работу. Молчание разрешением не является.
5. Выполни ровно один шаг. Не начинай следующий шаг в этой же сессии, даже если
   текущий оказался коротким.
6. Обнови `PROGRESS.md`: статус шага, дата, имя агента, ветка, ссылка на pull request,
   краткий итог, известные ограничения и что важно знать следующему агенту.
7. Закоммить изменения, запушь ветку и открой pull request.
8. Выведи отчёт по формату ниже.
9. Снова ОСТАНОВИСЬ и спроси разрешения на следующий шаг.

Правила журнала:

- `PROGRESS.md` обновляется в том же pull request, что и сам шаг.
- Статусы: `не начат`, `в работе`, `на ревью`, `выполнен`, `заблокирован`, `пропущен`.
- Если шаг заблокирован — укажи точную причину и что нужно, чтобы разблокировать.
  Не помечай шаг выполненным, если проверки не прошли.
- Ничего не удаляй из журнала. Новая запись добавляется, старая не переписывается.
- Имя ветки: `claude/step-NN-<slug>`, где NN и slug берутся из имени файла шага.

## Формат отчёта после каждого шага
1. Что найдено до изменения и какие существующие компоненты переиспользованы.
2. Изменённые файлы и миграции.
3. Реальный вывод команд сборки, тестов и миграций (вставить как есть).
4. Проверка безопасности и приватности.
5. Rollout и точная команда rollback.
6. Заключение: шаг завершён или заблокирован, и почему.
