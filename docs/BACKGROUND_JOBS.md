# Фоновые задания

BullMQ обслуживает только продуктовые и операционные задания. Интерактивный ход пользователя, доставка Telegram и память агента в очереди не переносятся.

## Компоненты

| Компонент | Назначение |
|---|---|
| `src/jobs/queue-registry.ts` | Разрешённые очереди и единый префикс |
| `src/jobs/bullmq-driver.ts` | Единственная точка импорта BullMQ |
| `src/jobs/envelope.ts` | Версия, idempotency key, trace и безопасная ссылка на payload |
| `src/jobs/job-outbox.ts` | Транзакционная публикация задания |
| `src/jobs/job-runs.ts` | Канонический журнал запуска, аренды и результата |
| `src/jobs/schedules.ts` | Расписания в PostgreSQL и reconciliation с очередью |
| `src/jobs/runtime.ts` | Timeout, AbortController, retry, DLQ и graceful shutdown |
| `src/jobs/maintenance.ts` | Диагностические сверки без самостоятельного исправления |
| `src/jobs/proactive/` | Напоминания, heartbeat и check-in |

## Данные

PostgreSQL хранит намерение, расписание, запуск и DLQ. Valkey хранит только восстановимое состояние очереди. Тексты сообщений, память, документы, секреты, платежные данные и медиа в payload BullMQ не помещаются; передаётся безопасная ссылка на каноническую запись.

## Исполнение

- Публикация выполняется из job outbox после commit бизнес-транзакции.
- `jobId` равен ключу идемпотентности.
- Временные ошибки повторяются с ограничением; постоянные уходят в DLQ; неопределённый результат внешней записи требует reconciliation.
- Потеря аренды, timeout или отмена прерывают обработчик через `AbortController`.
- Расписания сверяются с канонической таблицей при старте.
- Доставка пользователю выполняется только через durable Telegram outbox.

## Проактивные задания

Код детерминированно проверяет согласие, частоту, тихие часы, активность и уникальный слот. Если для формулировки сообщения нужен агент, используется служебная conversation Letta; результат не меняет память напрямую и не обходит обычные продуктовые инструменты.

`legacy`, `mirror` и `queue` задают единственного владельца расписания. Переход из mirror в queue выполняется человеком после серии совпавших выборок.

## Запланированные задачи

У наступившей задачи два рода, и разница в том, кто делает работу.

| `tasks.kind` | Что происходит в срок | Conversation |
|---|---|---|
| `reminder` | Ева сочиняет напоминание и отправляет его; дело делает человек | `scheduler` |
| `action` | Ева выполняет задачу своими инструментами и отдаёт результат | `task_action` |

Назначение `scheduler` запрещает инструменты полностью — сочинителю текста они не нужны. Назначение `task_action` не сужает набор: чем выполнять задачу, решает Letta. Точечно запрещены только изменения профиля: профиль человека меняется в разговоре с ним, а не фоновым ходом.

Границы автономного действия детерминированные и стоят в коде (`src/tasks/task-run.ts`):

- не более трёх попыток подряд с растущим отступом; исчерпав их, планировщик закрывает срок и говорит человеку прямо — напоминание доходит своим текстом, действие сообщает об отказе;
- не более двадцати выполненных действий на человека в сутки; упершаяся в потолок задача откладывается на час, а не теряется;
- действие, требующее подтверждения человека, в фоне не выполняется: спрашивать некого, поэтому вызов отклоняется, и Ева говорит об этом словами;
- один срок — одно выполнение: частичный уникальный индекс `task_events_delivery_once_idx`.

Формулировку задания собирает `scheduledInstruction` — общая для интервального планировщика и очереди: задача не должна выполняться по-разному в зависимости от того, какой механизм её забрал.
