## 2. Разрешённые противоречия

### 2.1. Восемь memory blocks против шести

Первый файл требует восемь блоков (`assistant_notes_and_recommendations`, `human`, `mental_map`, `persona`, `progress_notes`, `therapy_goals`, `tools`, `user_state`) и запрещает менять блок `tools`.

Фактическое состояние кода: `evaMemoryBlocks()` создаёт **шесть** блоков, блока `tools` не существует вовсе — это прямо зафиксировано в `docs/ARCHITECTURE.md`. Инвариант 12 в `CLAUDE.md` закрепляет шесть блоков.

**Решение: остаётся шесть блоков.** Восьмиблочная схема — легаси предыдущей архитектуры, её восстановление создало бы дублирующее хранилище рядом с PostgreSQL-моделью памяти из шагов 15–18. Смысл легаси-блоков сохраняется через отображение:

| Легаси-блок | Куда переносится |
|---|---|
| `mental_map` | `relationships_and_patterns` + граф `memory_nodes`/`memory_edges` |
| `therapy_goals` | `goals_and_commitments` + таблицы целей «ВЕКТОР» |
| `user_state` | `current_state` + `state_checkins` (шаг 51) |
| `progress_notes` | `progress_and_hypotheses` |
| `assistant_notes_and_recommendations` | `progress_and_hypotheses` + `insights` |
| `tools` | Не блок памяти. Видимость инструментов задаёт Tool Gateway (шаг 14) |

Требование «не менять блок `tools`» выполняется автоматически: менять нечего.

### 2.2. Психологический фокус против позиционирования

Первый файл допускает «психологический фокус» внутренних инструкций, второй прямо запрещает медицинские обещания. **Приоритет у второго.** Ева — ИИ-компаньон и ассистент по самопознанию и психологической самопомощи. Низкоинтенсивные образовательные и навыковые модули (КПТ, ACT, поведенческая активация) допустимы и не называются психотерапией.

### 2.3. Режим «провокационно-жёсткий»

Первый файл предлагает до пяти режимов тона, включая жёсткий, и упоминает легаси-метку «сучка». **Решение:** пять режимов сохраняются (`мягкий`, `сбалансированный`, `прямой`, `твёрдый`, `требовательный`). Легаси-метка не используется нигде, включая конфигурацию и админку. Для любого режима сохраняется запрет на унижение, угрозы, манипуляции и оскорбления; режим — версионируемый артефакт реестра из шага 13, а не свободная правка промпта.

### 2.4. Дневник

Первый файл описывает дневник со структурой «событие → эмоция → мысль → реакция → действие», второй — `life_journal_entries` с медиа, людьми и связями. Шаг 25 уже создаёт `journal_entries`. **Решение:** одна сущность `journal_entries` + `journal_entry_versions`, расширяется в шаге 51. Таблица `life_journal_entries` не создаётся.

### 2.5. Экран «Сегодня»

Оба файла описывают «Сегодня» по-разному. **Решение:** экран один, владелец — шаг 25. Шаги 51–54 добавляют на него блоки, не создавая второго дашборда. Нижняя навигация: «Сегодня», «Развитие», «Органайзер», «Пульт», «Профиль».

### 2.6. Учёт потребления

Первый файл требует единый ledger, шаг 27 уже проектирует аналитику себестоимости. **Решение:** ledger — путь записи, аналитика — путь чтения. Расширяется существующая `llm_requests` и `llm_spend_ledger`; новая `usage_events` создаётся только для нетокенных единиц (ASR-секунды, TTS-символы, отчёты, изображения). Второй финансовый контур запрещён.

### 2.7. Реестр проблем `USER_ISSUES`

**Решение:** не создаётся. Незавершённые темы — это узлы `memory_nodes` типа `problem` со статусами из шага 15 плюс цели в существующих таблицах. Отдельная таблица дублировала бы обе.

### 2.8. Лицензии на методики

Второй файл вводит жёсткий лицензионный шлюз. **Это принимается без смягчения** и становится инвариантом: доступность вопросника в интернете не даёт права на коммерческое электронное использование.

## Блок P5 — доступ, потребление и монетизация

### Шаг 34. Единый ledger потребления

- **Приоритет:** P5 · **Зависит от:** шаги 27, 10 · **Флаг:** `EVA_USAGE_LEDGER` · **Объём:** 1 PR · **Ветка:** `step/34-usage-ledger`

**ЦЕЛЬ.** Ввести один неизменяемый путь записи потребления, из которого читает аналитика шага 27.

**СНАЧАЛА ПРОВЕРЬ.** `llm_requests`, `llm_spend_ledger`, `usage_counters`, `quotas` и то, какие поля добавил шаг 27. Расширяй существующее, дубликаты не создавай.

**СДЕЛАЙ.**
1. Создай `usage_events` для единиц, которые не выражаются токенами: ASR-запрос, ASR-секунды, TTS-ответ, TTS-секунды и символы, распознавание изображения, генерация отчёта, генерация изображения, создание документа, web/YouTube-анализ, фоновое LLM-сообщение.
2. Каждое событие содержит `user_id`, тип, период, источник, провайдер и модель при допустимости, `correlation_id`, `idempotency_key`, количество, единицу измерения, стоимость при наличии и время.
3. Токенные события остаются в `llm_requests`; добавь ссылку `usage_event_id` для сквозной сверки.
4. Раздельно учитывай: сообщения пользователя, ответы Евы, входящие токены, исходящие токены, ASR, TTS, изображения, отчёты, документы, web-анализ, фоновые сообщения и напоминания.
5. Записи неизменяемы. Коррекции — отдельным событием со ссылкой на исходное. Прямое редактирование остатков запрещено.
6. Автоматическое напоминание, текст которого формировала LLM, учитывается как ответ согласно тарифной политике; напоминание без LLM не учитывается.

**НЕ ДЕЛАЙ В ЭТОМ ШАГЕ.** Не трогай квоты и подписки — это шаги 35–37. Не строй отчёты: чтение принадлежит шагу 27.

**ТЕСТЫ.** Повторная запись с тем же `idempotency_key` не создаёт дубль; коррекция не изменяет исходное событие; сумма по `usage_events` и `llm_requests` сходится с агрегатами шага 27; удаление пользователя очищает его события.

**ГОТОВО, КОГДА.** Каждый тарифицируемый вызов оставляет ровно одну запись, и её тип, количество и стоимость видны в аналитике.

**ОТЧЁТ.** По формату из `CLAUDE.md`.

### Шаг 35. Квоты, гранты и доступ Евы к собственным лимитам

- **Приоритет:** P5 · **Зависит от:** шаг 34 · **Флаг:** `EVA_QUOTA_POLICIES`, `EVA_ACCESS_GRANTS` · **Объём:** 1–2 PR · **Ветка:** `step/35-quotas-grants`

**ЦЕЛЬ.** Сделать бесплатную и платную политики раздельными, конфигурируемыми и наблюдаемыми, и дать Еве безопасный способ рассказать пользователю о его лимитах.

**СНАЧАЛА ПРОВЕРЬ.** Существующие `quotas`, `usage_counters`, транзакционное списание квоты и то, как оно связано с ходом.

**СДЕЛАЙ.**
1. Разведи политики: бесплатная — лимит сообщений за скользящий период; платная — суточный лимит ответов со сбросом в фиксированном часовом поясе. Обе задаются конфигурацией, не кодом.
2. Значения по умолчанию: бесплатных сообщений 10 за 24 часа; платных ответов 15 в сутки со сбросом в 00:00 Europe/Moscow. Меняются через Admin UI без правки кода.

4. Создай `state_checkins` и `state_checkin_factors`. Отметка занимает 20–40 секунд: настроение, энергия, напряжение, ясность, качество сна, удовлетворённость днём по шкале 1–10.
5. Дополнительные факторы: работа, общение, движение, отдых, питание, алкоголь, болезнь, погода, важное событие, пользовательский фактор.
6. Раздел не является медицинским мониторингом и так и обозначается.
7. Блоки «быстрая отметка состояния» и «последняя запись дневника» добавляются на существующий экран «Сегодня», второй дашборд не создаётся.

**НЕ ДЕЛАЙ В ЭТОМ ШАГЕ.** Не считай сигналы и корреляции — это шаг 54. Не создавай второй экран «Сегодня».

**ТЕСТЫ.** Запись сохраняется без участия ИИ; голосовая запись с исправлением транскрипции; связь с задачей и целью; удаление записи очищает индексы; отметка состояния не требует ИИ; чужая запись недоступна.

**ГОТОВО, КОГДА.** Дневник и состояние работают текстом и голосом и попадают на «Сегодня».

### Шаг 52. Ритмы, фокус и решения

- **Приоритет:** P9 · **Зависит от:** шаг 51 · **Флаг:** `EVA_LIFE_RITUALS`, `EVA_LIFE_FOCUS`, `EVA_LIFE_DECISIONS` · **Объём:** 2 PR · **Ветка:** `step/52-rituals-focus-decisions`

Ритуал содержит назначение, расписание, шаги, полную и минимальную версии, условия пропуска и связанные цели. Действия: полная версия, минимальная версия, пропустить сегодня, изменить, вернуться завтра. Штрафы, потеря серии и обвиняющие формулировки запрещены.

Карточка решения: название, контекст, почему важно, срок, варианты, факты, предположения, критерии, риски, обратимость, выбранный вариант, уверенность, дешёвый тест, дата пересмотра, фактический результат. Цикл: вопрос → варианты → факты и предположения → критерии → обратимость → дешёвый тест → решение → действие → пересмотр.

**ТЕСТЫ.** Пропуск ритуала не создаёт негативного сообщения; минимальная версия засчитывается; сессия фокуса переживает закрытие WebView; напоминание о пересмотре решения приходит по локальному времени; чужое решение недоступно.

**ГОТОВО, КОГДА.** Три модуля работают, связаны с целями и задачами и не давят на пользователя.

**ТЕСТЫ.** Программа продолжается после перерыва; минимальная версия дня засчитывается; отчёт при нехватке данных честно сообщает об этом; повторный запуск формирования отчёта не создаёт дубль.

**ГОТОВО, КОГДА.** Пользователь видит карту сфер, может пройти программу и получает честные периодические итоги.

**ЦЕЛЬ.** Дать безопасный бытовой модуль, не превращая его в медицинскую диетологию.

**СДЕЛАЙ.**
1. Создай `schedule_profiles`, `schedule_windows`: часовой пояс, рабочие дни и окна, учёба, дорога, сон, приёмы пищи, спорт, семейное время, тихие часы, окна для практик, исключения и отпуск. Часовой пояс определяется существующим `TimezoneResolver`; второй механизм не создаётся. В ход передаётся только локальное время, тип текущего окна и ближайшее допустимое окно, а не весь распорядок.
2. Добровольные данные образа жизни: возраст, рост, вес, уровень активности, цель, предпочтения и доступные продукты, бюджет, аллергии и ограничения, оборудование, опыт тренировок, заявленные травмы и противопоказания.
3. Функции: простой план рациона, список покупок, замены продуктов, распределение питания по распорядку, общие безопасные тренировки, минимальная версия занятия, состояние до и после, связь с ритмами и задачами.
4. Запрещено: диагностировать, назначать лечение, рекомендовать лекарства, гормоны и добавки, предлагать экстремальный дефицит, давать советы при беременности, расстройствах пищевого поведения и серьёзных заболеваниях без специалиста, гарантировать снижение веса, стыдить за вес.
5. При боли, головокружении или тревожных признаках занятие прекращается и рекомендуется медицинская оценка. Численные пределы считает код; модель только объясняет и предлагает варианты.

**ГОТОВО, КОГДА.** Модуль работает, не даёт медицинских рекомендаций и уважает распорядок пользователя.

## 7. Критерии приёмки второго слоя

Второй слой считается выполненным, если:

1. Учёт потребления раздельный по всем тарифицируемым единицам и виден пользователю и администратору.
2. Бесплатная и платная политики квот работают независимо и меняются конфигурацией.
3. Гранты расходуются через ledger и не отзываются после расходования.
4. Все четыре способа оплаты проходят через один контракт провайдера, а право доступа определяется фиксированным приоритетом.
5. Повторная покупка требует подтверждения и показывает корректную новую дату.
6. Уведомления об окончании подписки приходят за 3 дня, за 1 день и в день окончания без дублей.
7. Кнопки, опросы, контакты и файлы работают в обе стороны и продолжают тот же conversation без пустых дублей.
8. Набор memory blocks остался шестью; легаси-схема не восстановлена.
9. Режимы тона переключаются версией артефакта без пересоздания агента.
10. Распознавание и синтез речи настраиваются из админки, имеют резерв и попадают в себестоимость.
11. Документы, изображения, голос и MP3 обрабатываются безопасно и подключаются к базе знаний пользователя без смешивания данных.
12. Из записи встречи получается список договорённостей с ссылками на моменты записи, и задачи не создаются без подтверждения.
13. Ни одна методика не выдаётся без подтверждённого права коммерческого электронного использования.
14. Подсчёт баллов детерминирован, покрыт контрольными тестами и не выполняется моделью.
15. Тест и интервью можно прервать и продолжить; интервью работает текстом и голосом.
16. Любой автоматический вывод можно подтвердить, исправить, архивировать или удалить.
17. Сигналы «Моей жизни» не показываются при выборке менее пяти наблюдений и не выдают корреляцию за причину.
18. Живой портрет отключается, не перекрывает действия и не появляется во время теста.
19. Память прозрачна: пользователь видит источник каждого факта и управляет им из телефона.
20. Парный отчёт строится только при явных согласиях, не раскрывает сырые ответы и не выдаёт вердикт.
21. Раздел «Пользователи» позволяет решить типовую задачу поддержки целиком из интерфейса с аудитом каждого действия.
22. Каждая новая подсистема имеет административное или диагностическое представление.
23. Лендинг разворачивается вместе с проектом и берёт тарифы с сервера.
24. Кризисный протокол имеет приоритет во всех новых поверхностях.
25. Второй памяти, очереди, планировщика, RAG-контура, реестра версий и финансовой системы не появилось.
26. Все проверки, включая evals и нагрузочные сценарии, зелёные, а восстановление на чистом сервере сохраняет новые сущности.
