# Как запускать доработку Evaself

Инструкция для человека. Работает с любого устройства, включая телефон.

## Команда

Одна и та же для любого агента: Claude Code (веб или локально), Codex, другой.
Скопируйте целиком.

```
Работай в репозитории Viktor6886/evaself.

Продолжи roadmap по протоколу репозитория: восстанови текущий batch
из PROGRESS.md или возьми следующий, выполни его полностью и остановись.
```

Всё. Больше ничего вводить не нужно — команда одинакова на каждом batch.

Агент сам прочитает `PROGRESS.md`, поймёт, где остановилась работа, назовёт
номер batch и входящие в него шаги, выполнит их и остановится со сводкой.

## Что такое batch

Batch — единица работы: **одна ветка, один pull request, один прогон CI, одно
ревью**. Одна ваша команда = один batch. Всего 33 batch на 68 шагов.

Внутри batch агент работает автономно: шаг → targeted-тесты → коммит → пуш →
следующий шаг. В конце batch — полный прогон тестов, pull request, CI,
независимое ревью, мерж. Затем остановка.

Границы batch зафиксированы в `PROGRESS.md` и менять их нельзя.

**Запускайте batch, когда есть время довести его до pull request.** Пока
сессия идёт, прочитанное агентом переиспользуется; после перерыва в сутки всё
читается заново и оплачивается заново. Перерыв в полчаса ничего не стоит,
перерыв до завтра — стоит полного повторного чтения.

**Первый слой — архитектура и надёжность:**

| Batch | Шаги | Про что |
|---|---|---|
| 1–3 | 00–04 | Безопасность, изоляция данных, жизненный цикл хода, параллелизм |
| 4–10 | 05–13 | Восстановление, очереди, наблюдаемость, обновление SDK, админ-CRUD, версии |
| 11–15 | 14–22 | Инструменты, память, навыки, субагенты, evals |
| 16–20 | 23–30 | Знания, исследования, интерфейсы, аналитика, backup, нагрузка, приёмка |
| 21–23 | 31–33 | Опционально, только по отдельной команде |

**Второй слой — продукт. Начинается после шага 30:**

| Batch | Шаги | Про что |
|---|---|---|
| 24 | 34–37 | Учёт потребления, квоты и гранты, четыре способа оплаты, подписка |
| 25 | 38–40 | Кнопки, опросы, контакты, файлы, персона и режимы тона |
| 26 | 41–44 | Речь, документы и изображения, генерация файлов, встречи |
| 27 | 45–48 | Психологические методики: права, движок, импорт, экраны |
| 28 | 49–54 | Интервью, формулировка, дневник и состояние, ритмы, программы, сигналы |
| 29 | 55–58 | Практики, антистресс, живой портрет, прозрачная память |
| 30 | 59–60 | Контакты и дни рождения, приглашения и совместимость |
| 31 | 61–63 | Раздел «Пользователи», админка второго слоя, лендинг |
| 32 | 64–65 | Кризисный контур, итоговая приёмка второго слоя |
| 33 | 66–67 | Опционально: распорядок и питание, астрорефлексия |

## Настройка один раз перед стартом

Прежде чем запускать первый batch, включите защиту ветки `main`. Это
превращает правило «мержить только с зелёными проверками» из обещания агента
в запрет на стороне GitHub: даже если агент захочет смержить красный код, у
него не получится.

1. Откройте `https://github.com/Viktor6886/evaself/settings/branches`
2. **Add branch protection rule** (или **Add rule**)
3. В поле **Branch name pattern** впишите `main`
4. Включите галочки:
   - **Require a pull request before merging** — прямые пуши в main запрещены
   - **Require status checks to pass before merging** — и ниже в поиске
     отметьте все проверки CI, которые появятся в списке
   - **Require branches to be up to date before merging**
   - **Do not allow bypassing the above settings**
5. **Create** (или **Save changes**)

Галочку **Require approvals** не включайте — иначе агент не сможет мержить сам
и понадобится ваше нажатие на каждый batch.

Агенту предписано проверить наличие этой защиты перед первым мержем и
остановиться, если её нет.

## Что где лежит

| Файл | Что это |
|---|---|
| `CLAUDE.md` | Инварианты, безопасность, бюджеты, batch-протокол. Агент читает целиком. |
| `PROGRESS.md` | Где остановилась работа: текущий batch, шаг, ветка, статус, блокер. |
| `docs/IMPLEMENTATION_STATE.md` | Что уже реализовано и что переиспользовать вместо нового. |
| `docs/PROGRESS_HISTORY.md` | Архив записей по завершённым шагам. Агент читает только при разборе. |
| `docs/INVARIANT_DIVERGENCES.md` | Чем фактический код отличается от инвариантов. |
| `prompts/step-00…step-67` | 68 заданий. Агент берёт их сам. |
| `docs/EVASELF_LAYER2_PLAN.md` | План второго слоя. |
| `docs/*.docx` | Полные документы: техническое задание и промпт с анализом. |

## Что защищает от ошибок агента

| Защита | Как работает |
|---|---|
| Защита ветки `main` | GitHub физически не даёт смержить красный код |
| Независимое ревью | Автор изменения не оценивает сам себя: перед мержем работает отдельная проверка с чистым контекстом, ей передаются только задания batch и накопленный diff. Результат — комментарием в pull request |
| Проверка области изменений | Каждый изменённый файл должен быть отнесён к конкретному пункту задания. Файл «не пойми откуда» блокирует мерж |
| Запрет необратимого | Автономно нельзя `DROP TABLE`, `DROP COLUMN`, удаление данных, смену типов с потерей значений, правку секретов и продакшн-конфигурации |
| Восстановление `main` | Если после мержа `main` покраснел, агент обязан разобрать причину и починить вперёд отдельным pull request. Revert — только когда именно смерженное изменение доказанно сломало `main` и безопасного исправления нет |
| Выключенные feature flags | Смерженный код не работает, пока вы не включите флаг на сервере |
| `make update` | Делает резервную копию перед обновлением и откатывается сам при сбое проверок |

## Когда агент остановится сам

Штатная остановка одна — конец batch: сводка и ожидание вашей следующей
команды. Разрешения на мерж агент не спрашивает: смержит сам, как только
обязательные проверки зелёные, а независимое ревью дало три «да».

Красный CI, упавший тест, плавающий тест, недоступный перезапуск job —
не остановка. Агент обязан найти первопричину и починить: перезапустить job,
а если прав на перезапуск нет — устранить причину изменением кода, теста или
CI и прогнать проверки заново, столько раз, сколько нужно до зелёного
результата.

Аварийная остановка остаётся только там, где продолжать технически нечем.
Агент **не смержит** и остановится, если:

- нужен доступ, ключ, данные или продуктовое решение, которых у него нет;
- шаг требует необратимого изменения (`DROP TABLE` и подобное);
- шаг требует внешнего сервиса, недоступного в окружении;
- защита ветки `main` не включена;
- независимое ревью дало хоть один отрицательный ответ.

В этом случае он поставит `STATUS: заблокирован` в `PROGRESS.md`, заполнит
`BLOCKER`, оставит pull request открытым и объяснит причину. Невыполненный
пункт «ГОТОВО, КОГДА» или лишний файл в диффе к этому списку не относятся:
их агент доделывает и убирает, а не превращает в блокер.

## Что смотреть после batch

Агент выдаст сводку. Стоит проверить две вещи:

1. **Статус batch — `выполнен`?** Если `заблокирован` — причина в поле
   `BLOCKER` в `PROGRESS.md`.
2. **В отчёте по каждой проверке есть результат?** Формат — `команда → PASS`
   или `команда → FAIL` с разбором. Полный вывод зелёного прогона в отчёт не
   вставляется намеренно: он ничего не добавляет и стоит контекста. Если
   написано просто «всё хорошо» без перечня команд — попросите:
   `перечисли команды проверок batch NN и их результат`.

Если что-то не устраивает, откатить всегда можно:

```
Откати batch NN: создай revert-PR к соответствующему мержу и смержи его.
```

## Если сессия оборвалась

Просто дайте ту же команду в новой сессии. Агент восстановит состояние из Git
и `PROGRESS.md`: возьмёт ветку из поля `BRANCH`, сверит `LAST_COMMIT` и
продолжит с шага в поле `CURRENT_STEP`.

Ничего пересказывать агенту не нужно — и не нужно рассчитывать, что он помнит
предыдущую сессию. Всё, что нужно следующему агенту, лежит в `PROGRESS.md`.
Именно поэтому запрещено вести прогресс где-либо ещё: в переписке, в заметках
или в голове.

## Передача работы другому агенту

`CLAUDE.md` и `PROGRESS.md` написаны обычным текстом без привязки к конкретному
агенту. Чтобы продолжить в Codex, дайте ту же команду — он прочитает состояние
и продолжит с первого невыполненного batch.

Проверьте только, что в настройках Codex базовая ветка — `main`.

## Важно

- **Не запускайте два batch параллельно** в разных сессиях — они трогают одни
  файлы, конфликты гарантированы.
- **Мерж не включает функцию.** Все новые подсистемы приезжают выключенными
  через feature flag. Агенту запрещено включать их в production — это делает
  человек по инструкции из раздела ROLLOUT соответствующего шага. Так откат
  остаётся мгновенным: выключили флаг, а не откатывали код.
- **Код на GitHub ≠ код на сервере.** Чтобы обновить рабочую установку, на
  сервере выполняется `make update-preview`, затем `make update` — с резервной
  копией и автооткатом при сбое.

## Чего эти меры не убирают

Честно, чтобы не было сюрпризов:

- **Зелёный CI не значит «сделано правильно».** Он значит «собралось и старые
  тесты не сломались». Шаг может быть выполнен формально, но не по сути.
- **Независимое ревью делает тоже модель.** Оно ловит расхождения с заданием
  и лишние правки, но не заменяет инженера.
- **Накопление.** Внутри batch может быть до шести шагов, и ошибка первого
  обнаружится на последнем. Цена одного отката — весь batch, а не один шаг.
- **Реже CI — позже сигнал.** Полный прогон идёт на pull request, а не на
  каждый пуш. Поломка, которую ловит только CI, всплывёт в конце batch.
  Это осознанный размен: агент вместо ожидания CI на каждый checkpoint
  запускает targeted-тесты локально.
- **Ревью идёт на модели попроще.** Три фиксированных вопроса с обоснованием
  по строкам — задача, которая этого не требует. Но потолок у такого ревью
  ниже, чем у модели реализации.
- **Миграции.** Revert возвращает код, но применённую миграцию нужно откатывать
  отдельной down-миграцией. Поэтому разрушающие миграции автономно запрещены.

Что действительно снимает риск для боевой установки: **выключенные feature
flags**. Смерженный код лежит мёртвым грузом, пока вы не включите флаг. Не
включайте всё сразу — по одному, по инструкции ROLLOUT из соответствующего шага.
