# Как запускать доработку Evaself

Инструкция для человека. Работает с любого устройства, включая телефон.

## Команда

Одна и та же для любого агента: Claude Code (веб или локально), Codex,
любой другой. Скопируйте целиком.

```
Работай в репозитории Viktor6886/evaself.

Сначала перейди в корень репозитория — это каталог, в котором лежат файлы
CLAUDE.md, PROGRESS.md и каталог prompts/. Если ты сейчас не в нём, найди
корень командой git rev-parse --show-toplevel и перейди туда. Если репозиторий
не склонирован — склонируй его. Все пути ниже указаны относительно корня.

Дальше:
1. Прочитай CLAUDE.md и PROGRESS.md полностью.
2. Найди в PROGRESS.md первый шаг со статусом «не начат» и определи его порцию.
   Границы порций — строки с отметкой ⏸.
3. Назови мне номер порции, входящие в неё шаги и что собираешься сделать.
4. Выполни всю порцию по протоколу из раздела «Протокол выполнения шагов»
   в CLAUDE.md: задание из prompts/, проверки, обновление PROGRESS.md,
   pull request, независимая проверка, мерж по условиям, следующий шаг порции.
5. На отметке ⏸ остановись, выведи сводку по шагам порции и спроси
   разрешения на следующую порцию.

Ничего не делай сверх порции. При провале любой проверки не мержи: поставь
статус «заблокирован», объясни причину и остановись.
```

Всё. Больше ничего вводить не нужно — команда одинакова на каждой порции.

## Настройка один раз перед стартом

Прежде чем запускать первую порцию, включите защиту ветки `main`. Это
превращает правило «мержить только с зелёными проверками» из обещания агента
в запрет на стороне GitHub: даже если агент захочет смержить красный код, у
него не получится.

1. Откройте `https://github.com/Viktor6886/evaself/settings/branches`
2. **Add branch protection rule** (или **Add rule**)
3. В поле **Branch name pattern** впишите `main`
4. Включите галочки:
   - **Require a pull request before merging** — прямые пуши в main запрещены
   - **Require status checks to pass before merging** — и ниже в поиске
     отметьте все проверки CI, которые появятся в списке
   - **Require branches to be up to date before merging**
   - **Do not allow bypassing the above settings**
5. **Create** (или **Save changes**)

Галочку **Require approvals** не включайте — иначе агент не сможет мержить сам
и понадобится ваше нажатие на каждый шаг.

Агенту предписано проверить наличие этой защиты перед первым мержем и
остановиться, если её нет.

## Сколько это порций

Порция — 1–3 связанных шага. Всего 23 порции на 34 шага, то есть в среднем
полтора шага между остановками. Границы видны прямо в `PROGRESS.md` как
строки с ⏸.

| Порции | Шаги | Про что |
|---|---|---|
| 1–3 | 00–04 | Безопасность, изоляция данных, жизненный цикл хода, параллелизм |
| 4–10 | 05–13 | Восстановление, очереди, наблюдаемость, обновление SDK, админ-CRUD, версии |
| 11–15 | 14–22 | Инструменты, память, навыки, субагенты, evals |
| 16–20 | 23–30 | Знания, исследования, интерфейсы, аналитика, backup, нагрузка, приёмка |
| 21–23 | 31–33 | Опционально, только по отдельной команде |

## Что где лежит

| Файл | Что это |
|---|---|
| `CLAUDE.md` | Правила проекта и протокол автономной работы. Агент читает автоматически. |
| `PROGRESS.md` | Журнал: что сделано, что следующее, что важно знать следующему агенту. |
| `prompts/step-00…step-33` | 34 задания. Агент берёт их сам. |
| `docs/*.docx` | Полные документы: техническое задание и промпт с анализом. |

## Что защищает от ошибок агента

| Защита | Как работает |
|---|---|
| Защита ветки `main` | GitHub физически не даёт смержить красный код |
| Независимая проверка | Автор изменения не оценивает сам себя: перед мержем работает отдельная проверка с чистым контекстом, ей передаются только задание и diff. Результат — комментарием в pull request |
| Проверка области изменений | Каждый изменённый файл должен быть отнесён к конкретному пункту задания. Файл «не пойми откуда» блокирует мерж |
| Запрет необратимого | Автономно нельзя `DROP TABLE`, `DROP COLUMN`, удаление данных, смену типов с потерей значений, правку секретов и продакшн-конфигурации |
| Автооткат | Если после мержа `main` покраснел, агент обязан сделать revert, а не «чинить вперёд» |
| Выключенные feature flags | Смерженный код не работает, пока вы не включите флаг на сервере |
| `make update` | Делает резервную копию перед обновлением и откатывается сам при сбое проверок |

## Когда агент остановится сам

Кроме отметки ⏸, есть аварийная остановка. Агент **не смержит** и остановится, если:

- сборка или тесты красные;
- CI красный;
- хотя бы один пункт «ГОТОВО, КОГДА» не выполняется;
- независимая проверка дала хоть один отрицательный ответ;
- изменённый файл не относится ни к одному пункту задания;
- шаг требует необратимого изменения;
- нужен доступ, данные или продуктовое решение, которых нет;
- миграция не откатывается;
- защита ветки `main` не включена.

В этом случае он поставит в журнале статус `заблокирован`, оставит pull request
открытым и объяснит причину. Это нормальный исход, а не поломка.

## Что смотреть после порции

Агент выдаст сводку по шагам порции. Стоит проверить две вещи:

1. **Все шаги порции имеют статус `выполнен`?** Если есть `заблокирован` —
   прочитайте причину, она в `PROGRESS.md`.
2. **В отчёте есть реальный вывод команд?** Если написано просто «тесты прошли»
   без вывода — попросите: `вставь фактический вывод команд по шагу NN`.

Если что-то не устраивает, откатить всегда можно:

```
Откати шаг NN: создай revert-PR к соответствующему мержу и смержи его.
```

## Передача работы другому агенту

`CLAUDE.md` и `PROGRESS.md` написаны обычным текстом без привязки к конкретному
агенту. Чтобы продолжить в Codex, дайте ту же команду — он прочитает журнал и
продолжит с первого невыполненного шага.

Проверьте только, что в настройках Codex базовая ветка — `main`.

Именно поэтому запрещено вести прогресс где-либо ещё: в переписке, в заметках
или в голове. Всё, что нужно следующему агенту, должно быть в `PROGRESS.md`.

## Важно

- **Не запускайте две порции параллельно** в разных сессиях — они трогают одни
  файлы, конфликты гарантированы.
- **Мерж не включает функцию.** Все новые подсистемы приезжают выключенными
  через feature flag. Агенту запрещено включать их в production — это делает
  человек по инструкции из раздела ROLLOUT соответствующего шага. Так откат
  остаётся мгновенным: выключили флаг, а не откатывали код.
- **Код на GitHub ≠ код на сервере.** Чтобы обновить рабочую установку, на
  сервере выполняется `make update-preview`, затем `make update` — с резервной
  копией и автооткатом при сбое.
- **Если сессия оборвалась посреди порции** — просто дайте ту же команду в новой
  сессии. Агент прочитает журнал и продолжит с того места, где остановился.

## Чего эти меры не убирают

Честно, чтобы не было сюрпризов:

- **Зелёный CI не значит «сделано правильно».** Он значит «собралось и старые
  тесты не сломались». Шаг может быть выполнен формально, но не по сути.
- **Независимую проверку делает тоже модель.** Она ловит расхождения с заданием
  и лишние правки, но не заменяет инженера.
- **Накопление.** Даже при остановке каждые полтора шага ошибка может
  обнаружиться на два-три шага позже.
- **Миграции.** Revert возвращает код, но применённую миграцию нужно откатывать
  отдельной down-миграцией. Поэтому разрушающие миграции автономно запрещены.

Что действительно снимает риск для боевой установки: **выключенные feature
flags**. Смерженный код лежит мёртвым грузом, пока вы не включите флаг. Не
включайте всё сразу — по одному, по инструкции ROLLOUT из соответствующего шага.
