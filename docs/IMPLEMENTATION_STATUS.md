# Статус реализации интерфейсов

Evaself разговаривает с Letta через `@letta-ai/letta-agent-sdk` **0.7.1** —
это единственный conversational и когнитивный runtime (инвариант 3). Рядом с ним, и только
как административный control plane, подключён `@letta-ai/letta-client`
**1.12.1** (инвариант 4): он умеет то, чего нет в Agent SDK, и не создаёт
второго пути выполнения диалога.

Обе версии закреплены точно, без диапазона: `@latest` для SDK, CLI и GitHub
Actions запрещён. Матрица ниже — не список намерений: каждая строка со
статусом «метод» проверяется contract-тестом `test/letta-contract.test.ts`,
который ищет метод на живом объекте установленного пакета. Источник матрицы —
`eva-agent-service/src/letta/capabilities.ts`; расхождение реестра с
установленной версией красит прогон.

## Сверка с прежней версией

Задание шага 11 требует, чтобы contract-набор был воспроизводим и проходил на
обеих версиях. Написать его «до обновления» было уже невозможно: Agent SDK
уехал с 0.5.5 на 0.6.2 двумя групповыми обновлениями зависимостей раньше, чем
шаг начался, и прежней версии в репозитории не осталось. Поэтому сверка
сделана в обратную сторону — набор прогнан против 0.5.5, установленной
отдельно:

```
npm install --no-save --prefix /tmp/sdk055 @letta-ai/letta-agent-sdk@0.5.5
```

и проверен теми же путями, что и в `test/letta-contract.test.ts`.

Результат: **все двенадцать управляющих путей и все семь путей сессии
присутствуют и в 0.5.5, и в 0.6.2.** `agents.blocks` не было ни в той, ни в
другой — точечная запись в memory block жила в отдельном пакете всегда.

Это объясняет, почему молчаливое обновление ничего не сломало, и заодно
показывает, что набор выбран правильно: он описывает поверхность, на которой
runtime действительно держится, и версии сами по себе её не меняли. Ловит он
не «версия выросла», а «метода не стало» — плюс расхождение
`VERIFIED_VERSIONS` с установленным пакетом, чтобы следующий такой подъём
разбудил прогон, а не остался незамеченным.

## Чего матрица не доказывает

Contract-тесты выполняются офлайн: конструкторы обоих клиентов соединения не
открывают, и проверяется наличие метода, а не поведение операции на живом App
Server. Поэтому зелёный прогон означает «пакет тот, что проверяли», а не
«операция работает на этом развёртывании». Живая часть остаётся за
smoke-стендом и за сверкой при старте сервиса: расхождение с проверенной
матрицей всегда попадает в журнал, а флаг `EVA_LETTA_CONTRACT_VERIFY`
превращает его в отказ старта.

## Точечное изменение memory block

Официальная запись в блок существует — `agents.blocks.update` в letta-client,
и это единственный путь. Теневых значений блоков в PostgreSQL нет: таблица
`letta_memory_block_sync` удалена вместе с MemoryBlockSync (миграция 053).
Если официальная запись недоступна — флаг выключен, адрес control plane не
задан, App Server отверг операцию — операция честно отказывает. Записанным
блок не считается, пока запись не подтверждена.

Обычную память Ева ведёт сама: четыре блока и MemFS обслуживаются нативными
инструментами внутри хода, административный путь нужен только человеку.
