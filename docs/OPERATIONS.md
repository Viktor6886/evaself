# Эксплуатация

## Ежедневные команды

```bash
make status
make doctor
make check-search
make logs
make logs s=eva-agent-service
make logs s=letta-app-server
```

`make doctor` возвращает ненулевой код при критической ошибке, поэтому его
можно запускать из cron или systemd timer.

## Окно контекста

Предел контекста для Letta выводится из самой слабой включённой модели
(`llm_providers.context_window`) за вычетом ответа и запаса на постоянный
префикс — системный промпт, персону и описания инструментов. Он
объявляется conversation при первом ходе после старта сервиса.

Число это ПОЛНОЕ окно, а не одна лента сообщений: Letta получает его как
`context_window_limit` и меряет им весь собранный вход вместе с
префиксом. Поверх предела безопасности стоит бюджет
(`CONTEXT_BUDGET_TOKENS`), который предел только опускает — до того,
сколько мы согласны платить в каждом шаге хода.

**Ева подолгу думает перед ответом** — начинайте с `make check-latency`,
а не отсюда. Ход — это сумма стадий, и лечатся они разным: ожидание
слота пользователя, сборка контекста, ожидание сессии, генерация модели,
доставка. Разложение считается на каждом ходе и уходит в лог строкой
`Telegram turn обработан`; команда собирает его в таблицу с медианой и
p90 и рядом показывает задержку провайдера, число обращений на ход и
настройки, от которых ход становится долгим.

Частые причины, каждая со своим лечением:

| Что видно | Причина | Что делать |
|---|---|---|
| `reasoning_effort` выше `none` | модель думает дольше по прямому указанию | понизить в панели |
| велика `очередь пользователя` | ход ждал за фоновой работой: окно инициативы, проактивная задача | разнести окна, проверить расписания |
| велика `генерация целиком` при малой `до первого слова` | время уходит в вызовы инструментов | смотреть `avg_steps` |
| `retried`/`switches` больше нуля | провайдер отвечает с отказами, каждый повтор стоит секунд | проверить провайдера |
| велика `сборка контекста` | медленная база, а не модель | смотреть индексы |
| сжатие на каждом ходе | после префикса разговору осталось мало | `make check-tokens`, бюджет контекста |

Первое, на что смотреть в разделе «Обращения к модели», — `median_ms`
по провайдерам. Медиана в двадцать секунд означает, что ход не может
быть быстрым ни при каких настройках: это время самой модели, и
лечится оно сменой провайдера, а не бюджетом контекста.

Здесь же важное про `default_context_window`: заданное человеком число
СИЛЬНЕЕ выведенного кодом. Пока в настройках стоит явное значение,
бюджет из `contextLimit` не применяется вовсе. Чтобы вернуться к
выведенному, поле нужно очистить.

Пока этого не было, `default_context_window` оставался `NULL`, Letta не
знала, когда сжимать историю, и диалог рос до отказа модели: 770 000
токенов при окне 256 000. После такого отказа умирает любое сообщение,
включая «привет», и сам себя диалог уже не чинит.

Признак в чате владельца: «История диалога переросла окно модели: N
токенов при пределе M». Что делать:

1. убедиться, что у активных провайдеров заполнено окно контекста —
   раздел моделей административной панели. Значение по умолчанию 8192
   занижает предел для всех;
2. перезапустить `eva-agent-service`: предел объявляется conversation на
   первом ходе после старта, и Letta сожмёт историю сама;
3. если отказ повторяется — окно модели меньше, чем нужно постоянному
   префиксу, и помогает только модель с большим окном.

Явная настройка `default_context_window` сильнее выведенной: заданная
человеком остаётся как есть.

## Поиск

`make doctor` спрашивает у SearXNG `/healthz` и получает `200` даже тогда,
когда все движки заблокированы адресом дата-центра, а выдача пуста.
Контейнер жив, поиск не работает, и снаружи это выглядит одинаково: Ева
говорит «ничего не нашлось».

`make check-search` задаёт настоящий запрос из контейнера агента — тем же
путём, которым ходит Ева, — и показывает, кто ответил, а кто нет:

```bash
make check-search
make check-search q="курс евро"
```

Проверяются три случая: общий запрос, новости за неделю и погода. Строка
«не ответили» перечисляет движки, которые отказали или не уложились в
срок; выдача из одного движка вместо пяти — ещё не поломка, но уже
причина, по которой ответы стали хуже.

Что делать с результатом:

- **все движки в «не ответили»** — их блокирует адрес дата-центра. Состав
  движков в `searxng/settings.yml`; Mojeek и Qwant не блокируют и стоят
  там именно поэтому. Дальше — `docker compose logs searxng --tail 50`.
- **пусто только у новостей** — новостные движки блокируются чаще
  остальных. Ева при пустой выдаче сама снимает окно свежести и ищет
  заново, поэтому «за неделю» не обязано быть пустым в разговоре.
- **пусто только у погоды** — обычное дело: `wttr.in` и
  `duckduckgo weather` ломаются на разборе ответа, и это не блокировка
  по адресу, а поломка в самих движках. На поведение это не влияет:
  пустой раздел заставляет инструмент повторить запрос без раздела, и
  погода приходит обычной ссылкой, которую Ева дочитывает через
  `web_read`. Пустая строка в проверке — ожидаемая, а не тревожная.
- **crawl4ai не отвечает** — Ева найдёт ссылки, но не прочитает страницы:
  сниппет отвечает на «что было когда-то», а не на «сколько сейчас».

## LLM

```bash
make test-llm
make list-models
make configure-llm
```

Текущая конфигурация и результат последней проверки видны в
«Настройки LLM». При ошибке переключения смотрите оба сервиса:

```bash
make logs s=eva-agent-service
make logs s=letta-app-server
```

Не редактируйте `providers/auth.json` вручную. Конфигурацию записывает
официальный Letta CLI, а `eva-agent-service` координирует restart,
healthcheck и rollback.

## Agents, conversations и Letta

Всё в одной панели: `https://<домен>/admin`.

1. «Агенты» — список, поиск, владелец каждого агента и состояние его
   связки. Создание заводит личного агента человеку по Telegram ID тем же
   путём Letta Agent SDK, каким агент появляется при первом сообщении;
   повторный вызов для того же человека ничего не создаёт.
2. Карточка агента правит имя, описание, модель и видимость. Системный
   промпт здесь не правится: он общий для установки и живёт в разделе
   «Персона и промпт».
3. «Letta» → «Диалоги» — диалоги агента, состояние сессии, остановка
   идущего хода и архивация. История диалога открывается отдельной
   кнопкой, требует подтверждения в окне и попадает в журнал событий:
   кто и чей диалог открыл, без текста. Пароль при этом не спрашивается —
   он вводится один раз при входе в панель.
4. «Letta» → «Runtime» задаёт defaults новых объектов, memory filesystem,
   permission mode, dreaming и параметры пула сессий.

Удаление агента необратимо и отклоняется, пока идёт незакончившийся ход.
Выполняйте его только после backup.

## Панель с телефона

Панель рассчитана на телефон всерьёз: посмотреть, отвечает ли Ева, и
переключить провайдера — это делают в дороге, а не садясь за ноутбук.

Что из этого следует в работе:

- таблицы ниже 720 пикселей становятся карточками, и первое поле строки —
  её заголовок: список агентов ведёт человеком, список проверок — временем;
- меню прокручивается: разделов шестнадцать, и на короткий экран список
  целиком не помещается;
- диалоги приходят снизу, у большого пальца, и прокручиваются внутри себя;
- опасное действие требует набрать идентификатор цели, а не нажать «да»:
  «да» ставят не глядя, идентификатор приходится списать с экрана;
- канонический текст правится на весь экран — кнопкой «На весь экран»
  рядом с полем. Escape и переход в другой раздел его сворачивают.

## Персона и системный промпт

Раздел «Персона и промпт» правит настоящие production-источники:
`library/persona/eva.md` и `library/system/letta_local_memfs.md` остаются
значением по умолчанию, а правка становится версией в реестре артефактов.

Сохранение применяется сразу. Ответ панели называет, что именно
применилось: сколько агентов обновлено, сколько уже было на этой версии и
сколько отстало. Отставшие догоняются кнопкой «Синхронизировать» — она
ничего не меняет в тексте.

Если App Server был недоступен в момент сохранения, панель говорит об
этом прямо, а канонический текст всё равно зафиксирован: новые агенты
получат его сразу, существующие — следующей синхронизацией или своим же
ходом.

Откат возвращает предыдущую действующую версию, «Вернуть текст файла» —
то, что лежит в репозитории. И то, и другое — новая публикация: история
не переписывается.

Для произвольных OpenAI-compatible endpoints App Server использует свой
динамический адаптер `lmstudio`: это внутреннее имя connector, а не требование
устанавливать LM Studio. Он получает фактические ID через `/models` и отправляет
chat-completions на указанный Base URL. После переключения Evaself ждёт появления
выбранной модели в каталоге App Server; простой WebSocket healthcheck успешной
активацией не считается.
Сохранение настроек закрывает активные сессии; следующий запрос безопасно
переподключает их к той же conversation.

## Feature flags

```dotenv
EVA_PROFILE_COMPLETION_ENABLED=true
EVA_VECTOR_GOALS_ENABLED=true
EVA_PROFILE_CACHE_TTL_SECONDS=60
EVA_OUTBOX_ENABLED=true
```

После изменения выполните `docker compose up -d eva-agent-service`.
`EVA_OUTBOX_ENABLED=false` допустим только для диагностики: при прямой
доставке теряется гарантия повтора только Telegram-отправки. Памятью агента
ни один из этих ключей не распоряжается: она принадлежит Letta.

## Метрики turn

```bash
make logs s=eva-agent-service | grep 'Telegram turn обработан'
```

Строка разложена по этапам: ожидание слота, сборка контекста, ожидание
сессии Letta, первый срез ответа, генерация, синтез речи, доставка, общее
время и `db_query_count`. При тёплом cache ориентируйтесь на сумму
служебных этапов до `letta_generation_ms`; целевой порядок — до 100 мс, но
реальное значение зависит от VPS и измеряется только на развёрнутом стеке.

Жалобу «Ева долго отвечает» разбирают по `time_to_first_delta_ms`: ответ
показывается по мере генерации, поэтому воспринимается ход по времени до
первых слов, а не по `total_turn_ms`. Большой `queue_wait_ms` — это чужой
ход того же человека, большой `session_acquire_ms` — тесный пул сессий,
большой `time_to_first_delta_ms` при нормальной генерации — модель или
провайдер.

## Пользовательский WebApp

Mini App открывается на `https://<домен>/app/` только из Telegram. Разделы
«Сегодня», «Цели», «Прогресс» и «Профиль» используют HMAC-защищённый
`/public/*` API. Если интерфейс пишет «Откройте приложение из Telegram»,
проверьте URL Mini App у BotFather и актуальность bot token.

## База и связь объектов

```bash
make shell-db
SELECT * FROM v_agent_runtime;
SELECT name, model, is_active, last_check_ok FROM llm_providers;
SELECT * FROM sdk_settings;
```

Если у пользователя нет conversation, следующий `users/ensure` создаст его,
не удаляя агента. Зависшую блокировку хода можно снять из WebUI или маршрутом
`POST /v1/locks/{telegramId}/release`.

## Диск

```bash
df -h
docker system df
make disk-cleanup
```

`make disk-cleanup` не удаляет именованные volumes. Перед любыми ручными
операциями с volumes выполните `make backup`.

## Аварийный порядок

1. `make doctor`;
2. проверить логи проблемного сервиса;
3. `make restart`;
4. если проблема появилась после update — `make rollback`;
5. если повреждены данные — restore только из проверенного backup.

## Напоминания и история задач

Планировщик генерирует текст напоминания через тот же агент Евы и LLM Router:
`scheduler` использует `fast` в adaptive-режиме и выбранного provider в
single-режиме. Отправка напоминания создаёт `reminder_generated` и
`reminder_sent` в `task_events`, но не меняет задачу на `done`. Одноразовый
запуск отмечается `last_run_at`, поэтому повтор воркера не дублирует доставку.

В `task_events` сохраняются точный отправленный текст, Telegram message ID,
conversation и прямой `llm_request_id`; provider не угадывается по времени.
Ответ на конкретное сообщение Telegram связывается с задачей через
`reply_to_message.message_id`. «Сделал» завершает связанную задачу, «Завтра»
переносит, «Отмени» отменяет. Ева получает не более пяти кратких недавних
событий в runtime context и может запросить подробности user-scoped tools.
