# Security model

What Evaself actually protects, and what it does not.

## Attack surface

Exactly seven host names, all HTTPS, all through Caddy:

| Host | Auth | Notes |
|---|---|---|
| `<domain>` | none | static landing page |
| `app.<domain>` | none yet | Mini App shell; its `/public/*` API returns with the WebApp milestone |
| `api.<domain>` | none yet | only `/health`; `/v1/*` explicitly returns 404 |
| `n8n.<domain>` | n8n accounts | owner created on first visit |
| `admin.<domain>` | NocoDB accounts | `NC_INVITE_ONLY_SIGNUP=true` |
| `letta.<domain>` | Caddy basic auth (bcrypt) | console only; it reads through eva-agent-service |
| `status.<domain>` | none | optional, off by default |

Not reachable from the internet at all: PostgreSQL, Valkey, the Letta App
Server, eva-agent-service's `/v1/*`, SearXNG, the media service, the n8n worker, the
task runner, Crawl4AI, the backup helper.

## Host

* UFW: deny incoming, allow your existing SSH port + 80 + 443 (tcp+udp).
  **The installer never changes how you log in over SSH.**
* Fail2Ban on SSH: 5 attempts, 1 hour ban.
* `.env` is mode 600 and in `.gitignore`; `make doctor` fails if the mode
  drifts.
* Docker log rotation, so logs cannot fill the disk into an outage.

## Secrets

Generated by the installer, never committed, never in an image layer:

| | |
|---|---|
| 5 PostgreSQL passwords + 1 read-only role | 48 hex chars each |
| Valkey password, SearXNG secret, NocoDB JWT | 48 hex chars |
| `EVA_AGENT_API_KEY`, `LETTA_APP_SERVER_TOKEN` | 48 hex chars |
| `EVA_TELEGRAM_WEBHOOK_SECRET`, `N8N_RUNNERS_AUTH_TOKEN` | 48 hex chars |
| `N8N_ENCRYPTION_KEY` | 48 hex chars, generated **once**, ever |
| NocoDB / Letta console / n8n owner passwords | 20 chars, shown once |

The Letta console password is stored in `.env` as **plaintext for you**
and as a **bcrypt hash for Caddy** — Caddy never sees the plaintext, and
neither does the browser.

n8n credentials are exported to backups **encrypted**;
`N8N_ENCRYPTION_KEY` travels beside them, which is what makes a restore on
a new server possible.

## Request authentication

**n8n → eva-agent-service.** `X-API-Key`, compared with `timingSafeEqual`, so
the check is constant-time. Caddy 404s `/v1/*` on the public API host, so
even a leaked key is not usable from outside.

**Mini App → API.** Not implemented in this milestone. v0.1.0 verified
Telegram `initData` HMACs in the Python service that has been removed; the
same check returns with the WebApp API. Until then `app.<domain>` serves a
static shell whose data calls 404, and nothing accepts an unauthenticated
user id.

**Telegram → n8n.** `setWebhook` registers a `secret_token`; the first node
of the main workflow compares `X-Telegram-Bot-Api-Secret-Token` and drops
anything else. Guessing the webhook URL is not enough.

**eva-agent-service → App Server.** A capability token presented during
the WebSocket upgrade, held only by that one service. The console's Caddy
injects `X-API-Key` for eva-agent-service on the way out, so the browser
never holds either credential.

## Hermes

Root, no sandbox, by design — see [HERMES.md](docs/HERMES.md). Its only
boundary is a one-entry Telegram allowlist, which is why it uses a
separate bot and why `make hermes-status` prints the allowlist every time.

## What is deliberately not solved

Be clear-eyed about these:

* **The backup archive is not encrypted**, as specified. It contains
  every secret. Encrypt it before it leaves the server.
* **No rate limiting on Eva's public surfaces.** Quotas limit a *known*
  user's consumption; they do not stop a flood from an unknown one.
  Telegram's own rate limits are the first line of defence. If you expose
  Eva publicly at scale, put a rate limiter in front of Caddy.
* **No WAF, no IDS, no audit log of admin actions.** n8n and NocoDB
  actions are visible in their own logs and nowhere else.
* **There is no crisis screen yet.** v0.1.0 shipped a keyword-based one;
  it was removed together with the other full workflows when the
  architecture moved to the Agent SDK, and it returns with Eva's
  conversational logic. Do not put this in front of real users until it
  does.
* **`HERMES_YOLO_MODE=1`** means Hermes will not ask before running a
  destructive command. That is the trade for it being usable from
  Telegram.
* **Restoring a backup restores its `.env`**, including any secret you
  have rotated since. Rotate again after restoring an old archive.

## If a secret leaks

1. `make stop`
2. Rotate the affected value in `.env`.
   Two exceptions: `N8N_ENCRYPTION_KEY` (changing it destroys stored
   credentials — re-enter them instead) and the database passwords, which
   must be changed in PostgreSQL as well:
   ```bash
   make start
   make shell-db
   ALTER ROLE eva WITH PASSWORD 'new-value';
   ```
3. Revoke and re-issue Telegram tokens in @BotFather, LLM keys with the
   provider.
4. `make restart`, then `make doctor`.
5. Check `journalctl -u evaself-hermes` and the n8n execution list for
   anything you did not do.

## Reporting a vulnerability

Open a private security advisory on the repository. Please do not file a
public issue with a working exploit against a live installation.
