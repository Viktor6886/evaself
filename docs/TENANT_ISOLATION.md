# Граница арендатора

Документ описывает, как в Evaself устроен запрет на доступ к чужим
данным и что обязан сделать следующий шаг, добавляющий пользовательские
таблицы, фоновые задания или новые сервисы.

Реализация: `eva-agent-service/src/tenancy/`.
Тесты: `eva-agent-service/test/tenant-isolation.test.ts`.

## Правило

Запрос, затрагивающий таблицу из реестра `TENANT_TABLES`, выполняется
только внутри объявленной области. Области три:

| Область | Когда | Что разрешено |
|---|---|---|
| `user` | работа от имени одного человека: ход в Telegram, запрос Mini App, вызов инструмента, задание планировщика | каждая пользовательская таблица запроса ограничена столбцом владельца, и значение этого столбца совпадает с пользователем области |
| `system` | durable ingress и delivery, планировщик, вебхук оплаты до опознания владельца, телеметрия роутера | запрос ограничен владельцем; доступ сразу к нескольким пользователям требует явного `crossUser` с причиной |
| `admin` | административное API | нужна роль маршрута и запись в журнале аудита; без записи запрос не выполняется |

Области нет — запрос не выполняется. Это умолчание, а не исключение:
ошибиться в сторону отказа дешевле, чем в сторону утечки.

## Как это работает

1. `src/tenancy/tables.ts` — реестр пользовательских таблиц и столбцов
   владельца. Представления тоже в нём: они читаются как обычные
   источники.
2. `src/tenancy/sql.ts` — статический разбор запроса: какие
   пользовательские таблицы затронуты и ограничена ли каждая из них.
   Разбор не претендует на полноту парсера PostgreSQL: всё, что
   разобрать не удалось, считается НЕограниченным.
3. `src/tenancy/scope.ts` — сами области (AsyncLocalStorage) и проверка
   `assertQueryAllowed`. Она же сверяет значение: `user_id` из аргумента
   инструмента, тела запроса браузера или payload задания не пройдёт,
   если не совпадает с областью.
4. `Database` (`src/db.ts`) проверяет каждый запрос своего пула, а
   `guardPool` — пулы admin-api, llm-router, bootstrap и health-worker.

## Что обязан сделать следующий шаг

- **Добавил таблицу с `user_id`** — внеси её в `TENANT_TABLES`. Тест
  «каждая пользовательская таблица схемы объявлена в реестре» сверяет
  реестр с миграциями и падает, если таблица забыта. Если столбец
  `user_id` указывает не на пользователя Евы (как в `admin_sessions`),
  запиши таблицу в `NON_TENANT_USER_ID_TABLES` вместе с причиной.
- **Добавил фоновое задание** — открой область явно:
  `db.withSystemScope("причина", …)`, а работу от имени человека веди в
  `db.withUserScope({ userId, telegramId, label }, …)`. Идентификатор
  владельца бери из канонической записи, а не из payload задания.
- **Добавил маршрут админки, читающий данные пользователей** — поставь
  `tenantAccess: "cross-user"` в конфигурации маршрута. Тогда запись
  аудита создаётся и для безопасных методов, а без неё маршрут не
  получит доступа к данным.
- **Добавил сервис со своим пулом PostgreSQL** — оберни пул в
  `guardPool`. Отдельный тест ищет `new Pool(` без обёртки.
- **Пишешь поиск** — фильтр владельца ставится внутри выборки
  кандидатов, до ранжирования и агрегации. Проверка на графовом поиске
  уже есть, повтори её для нового контура.

## Чего граница не делает

- Не заменяет проверку владения связями. Если запрос принимает ссылку на
  объект (`goal_id`, `work_block_id`, `task_id`), владение проверяется
  отдельной выборкой до записи — граница не знает, чей это объект, пока
  он не назван в запросе.
- Не защищает от ошибок в самой схеме: строка без `user_id` остаётся
  строкой без владельца.
- Не является Row Level Security. RLS в PostgreSQL решал бы ту же задачу
  на стороне базы, но потребовал бы миграции, отдельной роли и передачи
  идентификатора в сессию соединения на каждый запрос из пула. Это
  отдельное решение с собственным планом отката; прикладная граница
  введена первой, потому что она обратима и проверяется тестами без
  поднятого PostgreSQL.
