# Жизненный цикл хода

Документ описывает, как ход пользователя становится одной записью, что в
этой записи есть, чего в ней нет и как её читать.

Реализация: `eva-agent-service/src/turns/`.
Миграция: `postgres/migrations/029_turn_lifecycle.sql`.
Тесты: `eva-agent-service/test/turn-lifecycle.test.ts`.
Флаг: `EVA_TURN_LIFECYCLE` (по умолчанию **выключен**).

## Зачем

До этого шага ход нигде не был единым объектом. Его следы разбросаны:
`telegram_updates` знает про приём и попытки, `telegram_outbox` — про
доставку, `llm_requests` — про модель, `usage_counters` — про списание.
Связать их можно было только вручную и только по времени, поэтому вопрос
«что произошло с этим ходом» ответа не имел.

`turn_runs` — одна строка на ход. `turn_transitions` — журнал его
переходов.

## Shadow-режим

Запись теневая в буквальном смысле:

- путь обработки сообщения не изменился;
- ответ пользователю от записи не зависит;
- сбой записи ход не роняет — каждый метод `TurnLifecycle` гасит свою
  ошибку в лог и возвращает управление.

Это проверяется тестами: с включённым флагом и без него ответ и результат
хода совпадают, а при базе, отказывающей на каждом запросе, пользователь
всё равно получает ответ.

Согласованный бюджет теневой записи — не более 250 мс на ход сверх
времени без неё.

## Ключ идемпотентности

`канал:идентификатор события:conversation`, например `telegram:90210:-`.
Для Telegram conversation в момент приёма ещё не известен, и его место
занимает `-`: ход телеграм-апдейта ровно один. Повторная доставка того же
апдейта второй записи не создаёт — растёт только `attempt`.

## Состояния

Список состояний взят из `CLAUDE.md` дословно и синонимов не имеет
(`src/turns/states.ts`). Переход, которого нет в графе, отклоняется кодом
и попадает в `turn_transitions` с `error_code = 'invalid_transition'` —
в shadow-режиме это диагностика, а не отказ обслуживания.

Прямой путь Telegram-хода:

```
accepted → queued → claimed → context_building → context_built
        → sent_to_letta → letta_processing → result_received
        → outbox_committed → delivering → delivered → completed
```

Ход, прекращённый до обращения к модели (блокировка, исчерпанная квота,
неподдерживаемое сообщение, команда, провал распознавания), идёт
`cancelling → cancelled` с безопасной причиной в `cancel_reason`. Ответ
пользователю при этом отправляется: прекращён ход модели, а не диалог.

Из любого незавершённого состояния достижимы отмена и отказ: ход
обрывается снаружи — перезапуском, отменой, недоступным App Server, — и
запрещать эти переходы значило бы запрещать правду.

`tools_pending` и `approval_pending` граф допускает, но Telegram-ход их
пока не пишет: SDK выполняет инструменты внутри одного вызова и
промежуточной точки наблюдения не даёт. Их заполнит шаг, который введёт
пошаговое исполнение.

`delivered` означает «сообщение поставлено в outbox и попытка отправки
сделана», а не «Telegram подтвердил доставку». Если строку outbox не
удалось сразу забрать, её досылает фоновый воркер, а запись хода уже
помечена доставленной. Подтверждение от Telegram живёт в
`telegram_outbox.status`, и связь с ходом даёт `outbox_id`.

Ход, переживший перезапуск процесса посреди работы (например, в
`context_building`), при повторном проходе воркера сначала получит
несколько отклонённых переходов и только потом продолжится. Запись
остаётся связной и `run_id` тот же, но в `turn_transitions` появляется
шум `invalid_transition`, который легко принять за настоящую аномалию.
Это лечится шагом 5, который вводит настоящее восстановление хода; до
тех пор такой шум — известное поведение, а не находка.

## Что в записи есть и чего нет

Есть: канал, владелец, `update_id`, агент, conversation, назначение,
состояние, номер попытки, аренда исполнителя, барьер отмены, метрика и
факт списания квоты, строка outbox, сессия Agent SDK, трасса, версии
prompt и flow, безопасный код ошибки, времена и длительности.

Нет и не будет: промптов, ответов модели, аргументов инструментов,
reasoning, текста ошибки провайдера. Хранится структура хода, а не его
содержание (инвариант 19). Отдельный тест проверяет, что ни один
фрагмент пользовательского текста в запись не попадает.

`prompt_version` — отпечаток действующего промпта (персона плюс
системный промпт), а не ссылка в реестр: реестра версий промптов в
проекте нет, и заводить его этот шаг не вправе. `llm_request_id`
остаётся пустым: ход обращается к модели через App Server и записи
роутера не видит.

## Граница арендатора

`turn_runs` — пользовательская таблица (`user_id`, `telegram_user_id`),
она внесена в `TENANT_TABLES`. Каждый запрос к ней несёт столбец
владельца: обращение по одному `run_id` граница не пропустит. Владелец
выбирается один раз в начале хода и на полпути не меняется. Столбец
подставляется кодом, поэтому статический разбор его не видит — у этих
запросов стоит пометка `-- tenant: by owner`, а настоящую проверку
выполняет граница в рантайме.

`turn_transitions` владельца не хранит: строки в ней адресуются только
через `run_id`, а он уже под границей.

## /metrics

Prometheus-совместимая выдача на `/metrics`, закрытая тем же внутренним
ключом, что и `/v1`. Ключ нужен не потому, что там есть личные данные
(их там нет), а потому что глубина очередей и состояние пула — подсказка
тому, кто ищет, когда сервису тяжелее всего.

| Метрика | О чём |
|---|---|
| `eva_inbox_pending`, `eva_inbox_oldest_age_seconds` | глубина и возраст durable inbox |
| `eva_outbox_pending`, `eva_outbox_oldest_age_seconds` | глубина и возраст durable outbox |
| `eva_turns_active{state}`, `eva_turns_active_total` | незавершённые ходы |
| `eva_turn_wait_ms{stat}`, `eva_turn_duration_ms{stat}` | ожидание и длительность хода за час |
| `eva_user_locks{state}` | блокировки пользователей: удерживаемые и в очереди |
| `eva_letta_sessions{state}` | сессии Agent SDK: занятые ходом и простаивающие |
| `eva_postgres_pool_connections{state}` | пул PostgreSQL |
| `eva_event_loop_lag_seconds{quantile}` | лаг event loop |
| `eva_turn_lifecycle_enabled` | включён ли флаг — без него метрики ходов нулевые |

Недоступная база выдачу не роняет: метрики остаются, значения
обнуляются. Метрики нужны в том числе тогда, когда что-то сломалось.

## Включение и откат

Включение: `EVA_TURN_LIFECYCLE=true` в `.env`, перезапуск
`eva-agent-service`. Откат: вернуть `false` и перезапустить — запись
прекращается, ход идёт прежним путём, уже накопленные строки остаются.
Полный откат схемы: `postgres/migrations/down/029_turn_lifecycle.sql`.
