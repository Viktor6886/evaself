# Обновление и rollback

```bash
make update-preview
make update
make rollback
```

Все версии зафиксированы в `versions.env`; плавающие `latest`/`stable` не
используются.

## Что обновляется само, а что приходит из репозитория

Это разные источники, и путать их дорого.

**Из реестров образов** `make update` подтягивает теги сторонних сервисов —
PostgreSQL, Valkey, Caddy, SearXNG, Crawl4AI, Uptime Kuma. Список
задан в `scripts/latest-versions.py`; мажорные версии он помечает как
`MAJOR — manual` и сам не поднимает. `make update-preview` показывает эту
разницу, ничего не меняя.

**Из репозитория** приходит всё остальное, и в первую очередь версии Letta.
`LETTA_AGENT_SDK_VERSION`, `LETTA_CODE_VERSION` и `LETTA_CLIENT_VERSION` в
опросе реестров не участвуют вовсе: их выводит из lock-файла агента
`scripts/ci/sync-letta-versions.py`, а обязательная проверка CI не пускает
состояние, где они разошлись. На сервер приезжает та версия App Server,
которая проверена в `main` вместе с кодом, — обновиться «сама по себе» она
не может, и клиент с рантаймом разъехаться тоже.

`make update`:

1. создаёт полный backup;
2. сохраняет текущий commit и `versions.env`;
3. получает новые версии и собирает образы;
4. применяет идемпотентные migrations;
5. запускает стек и `make doctor`;
6. автоматически выполняет rollback при неуспешной проверке.

Migration 004 добавляет реестр LLM и не удаляет старые данные. Для
существующей установки отдельный `LLM_CONFIG_ENCRYPTION_KEY` нужно создать
через `make configure`. Подстановка `EVA_AGENT_API_KEY` вместо него —
устаревший путь совместимости: он существует только потому, что на таких
установках этим значением уже зашифрованы строки реестра. Сервис называет
эту подстановку в предупреждениях конфигурации при запуске, `llm-router`
её не принимает вовсе, а новая установка получает отдельный ключ от
установщика — его отсутствие там означает ошибку настройки, а не
умолчание.

Migrations `008`–`013` совместимо добавляют Telegram inbox/outbox, локаль,
профиль, цели и purpose conversations. Они не создают память агента:
conversations, история, memory blocks и MemFS принадлежат Letta. Не
откатывайте migrations ручным удалением таблиц: `make rollback` возвращает
код и версии образов, а схема откатывается только проверенным down-файлом.

Migration `028` добавляет managed LLM routing и `task_events`. Она оставляет
режим `adaptive`, сохраняет существующие providers и chains, а новые цепочки
заполняет только если они пусты (`fast` из chat,
`research` и `safety` из deep/chat, `vision` только совместимыми providers).
Обычный `make update` применяет её автоматически; ручной SQL и
перенастройка Letta не нужны. Парный down-файл предназначен для проверяемого
отката схемы, но production rollback по-прежнему начинайте с backup.

После обновления:

```bash
make doctor
make test-llm
make shell-db
SELECT version FROM schema_migrations ORDER BY version;
```

Rollback возвращает код и версии образов, но не обращает назад уже
применённые совместимые migrations. Поэтому backup перед update обязателен.

## Что `make update` делает сам

Одна команда закрывает весь цикл — ручных шагов после неё нет:

0. проверка, что развёрнутое совпадает с рабочим деревом. «Скачивать
   нечего» и «работает то, что лежит в файлах» — разные вещи: после смены
   ветки или неприменённого checkout новые файлы уже на диске, а
   контейнеры и база остаются на старом коде. Команда сравнивает HEAD с
   `.rollback/deployed` и прогоняет цикл целиком, если они разошлись.
   Принудительно — `make update-force`;
1. зашифрованный backup и точка отката в `.rollback/`;
2. **локальные правки убираются в `git stash`**, если рабочее дерево грязное
   (раньше это молча отменяло обновление кода). Ничего не теряется:
   `git stash pop` возвращает всё обратно, команда печатает и список
   изменений, и способ их вернуть;
3. **возврат на релизную ветку.** Установка, застрявшая на feature-ветке
   или на detached HEAD после `make rollback`, продолжает рапортовать об
   успешных обновлениях, ничего при этом не получая. Переключение
   происходит автоматически, но только когда на текущей позиции нет
   собственных коммитов — потерять работу оно не может. Если они есть,
   команда предупреждает и не трогает ничего;
4. `git pull --ff-only`;
5. создание мастер-ключа Secret Store, если его ещё нет;
6. **`scripts/ensure-env-defaults.sh` добавляет в `.env` настройки, которые
   появились в `.env.example` с момента установки.** Существующие значения
   не трогаются никогда, новые секреты генерируются, пароли БД и админов —
   нет: их выдумывание отрезало бы стек от собственных данных, о таких
   случаях команда предупреждает отдельно;
7. сборка образов, миграции, пересоздание контейнеров, повторные миграции;
8. удаление устаревшей плоской сети `evaself-network`, если на ней уже
   никого не осталось;
9. финализация админ-панели;
10. `make doctor`, а при его провале — автоматический откат.

### NocoDB удалён: что остаётся на сервере

Табличный интерфейс NocoDB убран из стека целиком — сервис, профиль, домен,
маршрут Caddy, секреты и скрипт синхронизации. Ева от него никогда не
зависела: ни один сервис к нему не обращался, а разделы данных есть в
административной панели.

Обновление **не удаляет данные** — ни автоматически, ни украдкой. На
установке, где профиль был включён, останутся:

- база `nocodb` с метаданными самого NocoDB (данные Евы живут в `eva` и
  не затронуты);
- роль PostgreSQL `nocodb`;
- том Docker `evaself_nocodb_data`;
- строки `NC_*` и `NOCODB_DB_*` в `.env`;
- запись `nocodb` в `COMPOSE_PROFILES`, если она там была.

Всё это ничего не делает и никому не мешает. Когда убедитесь, что
интерфейс не нужен, уберите остатки вручную — команды необратимы, поэтому
и не выполняются за вас:

```bash
docker rm -f evaself-nocodb 2>/dev/null || true
docker volume rm evaself_nocodb_data

make shell-db
DROP DATABASE nocodb;
DROP ROLE nocodb;
```

Строки `NC_*` и `NOCODB_DB_*` из `.env` можно удалить тем же движением;
`ensure-env-defaults.sh` их больше не добавляет. Резервные копии,
сделанные до удаления, по-прежнему содержат дамп базы `nocodb` — восстановить
её при необходимости можно из них.

### Мастер-ключ

При первом создании ключа команда печатает предупреждение. Отнеситесь к нему
серьёзно: `secrets/eva-secrets-master-key` шифрует резервные копии и **в них
самих не содержится**. Потеря файла означает, что ни один архив не
восстановить. Скопируйте его за пределы сервера сразу.
