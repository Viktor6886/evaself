# База знаний и векторный индекс Qdrant

Решение владельца 2026-09-29: векторный индекс базы знаний — Qdrant. Прежний
запрет Qdrant в `CLAUDE.md` снят; новая формулировка — инвариант 14.
Остальные инварианты не меняются.

## Граница

| PostgreSQL владеет | Qdrant хранит |
|---|---|
| документами, их версиями, хэшами, статусами | вектор фрагмента |
| текстом фрагментов, страницами, разделами | `chunk_id`, `document_id` — ссылку обратно |
| владельцем документа и коллекциями общей базы | `user_id` / `collection_id` — для фильтра |
| настройками, версиями эмбеддингов, аудитом | модель и версию эмбеддинга точки |
| лексическим поиском: FTS и pg_trgm | ничего сверх этого |

- **Qdrant — производный индекс.** Всё в нём выводится из PostgreSQL.
  Потерянный том перестраивается командой «Перестроить индекс» (K3), а не
  восстанавливается из архива: том Qdrant в `make backup` не входит.
  Снимки (`POST /collections/{c}/snapshots`) допустимы как ускорение, но не
  заменяют перестройку.
- **Не память агента.** Recall, Memory Blocks и MemFS — Letta. В Qdrant нет
  переписки, заметок, блоков памяти и выводов о человеке.
- **Не второй RAG-контур.** Искать или нет, решает Ева: `knowledge_search` —
  продуктовый инструмент, который Letta вызывает сама. Найденное не
  подмешивается в каждый ход, отдельного LLM-вызова «что вспомнить» нет.
- **Документы — данные, а не инструкции.** Текст фрагмента, попавший в ответ
  инструмента, помечается как содержимое документа; команды из него не
  выполняются (K4).

## Размещение

- Контейнер `qdrant` (`versions.env`: `QDRANT_IMAGE`, `QDRANT_VERSION`,
  образ `-unprivileged`, uid 1000), том `evaself_qdrant_data`, лимит памяти
  `QDRANT_MEM_LIMIT`.
- Сеть `evaself-vector` — внутренняя, без выхода наружу. В ней только
  Qdrant и серверные процессы Evaself: `eva-agent-service`, `admin-api`,
  `health-worker`. Портов наружу нет; Mini App, Telegram и браузер
  администратора до Qdrant не достают.
- `QDRANT_API_KEY` генерирует установщик (`configure.sh`,
  `ensure-env-defaults.sh`). Без ключа индекс не используется, поиск идёт
  по PostgreSQL; `doctor.sh` об этом предупреждает.
- Healthcheck — `/readyz` через `bash /dev/tcp` (в образе нет curl и wget).
  `/readyz` и `/healthz` отвечают без ключа, всё остальное, включая
  `/metrics` самого Qdrant, — только с ключом.
- Каталог служб панели: `qdrant` (группа «Хранилища») — состояние и
  перезапуск.
- `make update` берёт у Qdrant только исправления внутри минорной версии:
  хранилище гарантированно открывается лишь следующей минорной, поэтому
  переход на новую минорную — выпуск этого репозитория, по одной за раз.
- `eva-agent-service` зависит от Qdrant необязательно: без него сервис
  стартует, а поиск работает в degraded.

## Коллекции и версии

Две физические коллекции на версию эмбеддингов:

| Коллекция | Что | Граф HNSW | Индексы payload |
|---|---|---|---|
| `eva_knowledge_private_v<N>` | личные базы | `m=0`, `payload_m=16`: графы по людям | `user_id` (keyword, `is_tenant`), `document_id` |
| `eva_knowledge_global_v<N>` | общая база администратора | `m=16` | `collection_id`, `document_id` |

Приложение ищет через alias `eva_knowledge_private` и `eva_knowledge_global`.
Смена модели — новая пара коллекций, переиндексация в фоне, проверка полноты
и качества, затем перевод обеих alias одним запросом. Прежняя версия
остаётся для отката (тот же перевод alias назад) и удаляется отдельной
командой; активную версию удалить нельзя.

Коллекций на человека нет: личная база — одна коллекция с полем-арендатором.
Шардирование по `user_id` (custom sharding Qdrant) добавляется без смены
формата точек, если одна коллекция перестанет помещаться.

Идентификатор точки — `knowledge_chunks.id`. Повтор записи заменяет точку,
поэтому индексация идемпотентна и возобновляема.

Payload точки — только `chunk_id`, `document_id`, `user_id`,
`collection_id`, `page_start`, `page_end`, `section`, `mime`,
`embedding_model`, `embedding_version`, `created_at`. Текста фрагмента в
Qdrant нет: он читается из PostgreSQL по `chunk_id`. Хранить текст в payload
имеет смысл только после замера, который покажет выигрыш.

## Изоляция арендаторов

Фильтр строит только `src/knowledge/vector-store.ts`:

- `searchPrivate(userId, …)` всегда добавляет `user_id = <владелец>`;
  интерфейса личного поиска без владельца нет. `userId` приходит из
  серверного контекста хода или сессии — не из аргументов модели, Telegram,
  Mini App или браузера.
- Точка, чей `user_id` не совпал с фильтром, отбрасывается, даже если Qdrant
  её вернул.
- Общий поиск ходит только в коллекцию общей базы и только по включённым
  коллекциям; пустой список — пустой ответ, а не поиск по всему.
- Запись проверяет область: у личной точки есть владелец и нет коллекции,
  у общей — наоборот.

Проверки: `eva-agent-service/test/qdrant-vector-store.test.ts` (что уходит
в Qdrant) и `scripts/ci/test-qdrant.mjs` (что Qdrant с этим делает: точка
чужого человека ближе к запросу, но не находится).

## Отказ Qdrant

Отказ Qdrant не роняет разговор. Коды `QdrantError`:

| Код | Что значит | Что делает поиск |
|---|---|---|
| `qdrant_unavailable`, `qdrant_timeout`, `qdrant_server_error` | сбой сервиса (`transient`) | degraded: FTS + pg_trgm, `degraded=true` |
| `qdrant_cancelled` | ход отменён вызывающим | ничего: запрос не уходит, повторять нечего |
| `qdrant_not_found` | alias ещё не создан — индекс не включали | пустой векторный результат |
| `qdrant_unauthorized` | неверный `QDRANT_API_KEY` | degraded и ошибка в статистике |
| `qdrant_bad_request` | ошибка вызывающего (размерность, фильтр) | ошибка с описанием Qdrant |

Описание отказа Qdrant («Vector dimension error: expected dim: 4, got 3»)
доходит до панели: в нём имена полей и числа, но не ключ и не текст
документов. Текст исключения `fetch` не пересказывается.

## Метрики

`/metrics` агента (без запросов, документов и идентификаторов в метках):

| Метрика | Требование задания |
|---|---|
| `eva_qdrant_latency_ms_{sum,count,max}{operation="search"}` | `qdrant_search_latency` |
| `eva_qdrant_errors_total{operation="search"}` | `qdrant_search_errors` |
| `eva_qdrant_latency_ms_*{operation="upsert"}`, `eva_qdrant_errors_total{operation="upsert"}` | `qdrant_upsert_latency`, `qdrant_upsert_errors` |
| `eva_knowledge_stage_latency_ms_*{stage="embedding"}`, `…errors_total` | `embedding_latency`, `embedding_errors` |
| `eva_knowledge_stage_latency_ms_*{stage="rerank"}` | `rerank_latency` |

`qdrant_points`, `knowledge_indexing_lag`, `knowledge_indexing_failed` и
`rebuild_progress` появляются вместе с индексацией (K3): их источник —
таблицы PostgreSQL.

## Проверка отсутствия эквивалента (правило 20)

K1:

- **Служба `qdrant`.** Векторного хранилища кроме pgvector в составе нет;
  pgvector остаётся откатом и не заменяется в этом batch. Qdrant не
  дублирует PostgreSQL: он хранит только производный индекс.
- **Сеть `evaself-vector`.** Существующая `data` отдаёт PostgreSQL и Valkey
  всем процессам данных; Qdrant в ней был бы доступен тем, кому он не нужен.
  Отдельная внутренняя сеть — меньше прав при той же схеме сегментации.
- **`src/knowledge/qdrant-client.ts`.** Клиента Qdrant в коде нет;
  `@qdrant/js-client-rest` не взят сознательно: нужно полтора десятка
  вызовов, а пакет тянет генерированный клиент всего API. HTTP-вызов с
  таймаутом и кодами — тот же подход, что у клиента Router.
- **`src/knowledge/vector-store.ts`.** Прежний векторный поиск —
  SQL в `src/knowledge/search.ts`, фильтра арендатора для внешнего индекса
  в коде нет. Модуль — единственное место, где строится фильтр Qdrant.
- **`src/knowledge/metrics.ts`.** Повторяет устройство
  `src/tools/tool-metrics.ts` (счётчики модуля, рендер в `MetricsCollector`);
  реестра метрик, куда их можно было бы добавить без нового модуля, нет.
