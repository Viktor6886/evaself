# База знаний и векторный индекс Qdrant

Решение владельца 2026-09-29: векторный индекс базы знаний — Qdrant. Прежний
запрет Qdrant в `CLAUDE.md` снят; новая формулировка — инвариант 14.
Остальные инварианты не меняются.

## Граница

| PostgreSQL владеет | Qdrant хранит |
|---|---|
| документами, их версиями, хэшами, статусами | вектор фрагмента |
| текстом фрагментов, страницами, разделами | `chunk_id`, `document_id` — ссылку обратно |
| владельцем документа и коллекциями общей базы | `user_id` / `collection_id` — для фильтра |
| настройками, версиями эмбеддингов, аудитом | модель и версию эмбеддинга точки |
| лексическим поиском: FTS и pg_trgm | ничего сверх этого |

- **Qdrant — производный индекс.** Всё в нём выводится из PostgreSQL.
  Потерянный том перестраивается командой «Перестроить индекс» (K3), а не
  восстанавливается из архива: том Qdrant в `make backup` не входит.
  Снимки (`POST /collections/{c}/snapshots`) допустимы как ускорение, но не
  заменяют перестройку.
- **Не память агента.** Recall, Memory Blocks и MemFS — Letta. В Qdrant нет
  переписки, заметок, блоков памяти и выводов о человеке.
- **Не второй RAG-контур.** Искать или нет, решает Ева: `knowledge_search` —
  продуктовый инструмент, который Letta вызывает сама. Найденное не
  подмешивается в каждый ход, отдельного LLM-вызова «что вспомнить» нет.
- **Документы — данные, а не инструкции.** Текст фрагмента, попавший в ответ
  инструмента, помечается как содержимое документа; команды из него не
  выполняются (K4, «Поиск»).

## Размещение

- Контейнер `qdrant` (`versions.env`: `QDRANT_IMAGE`, `QDRANT_VERSION`,
  образ `-unprivileged`, uid 1000), том `evaself_qdrant_data`, лимит памяти
  `QDRANT_MEM_LIMIT`.
- Сеть `evaself-vector` — внутренняя, без выхода наружу. В ней только
  Qdrant и серверные процессы Evaself: `eva-agent-service`, `admin-api`,
  `health-worker`. Портов наружу нет; Mini App, Telegram и браузер
  администратора до Qdrant не достают.
- `QDRANT_API_KEY` генерирует установщик (`configure.sh`,
  `ensure-env-defaults.sh`). Без ключа индекс не используется, поиск идёт
  по PostgreSQL; `doctor.sh` об этом предупреждает.
- Healthcheck — `/readyz` через `bash /dev/tcp` (в образе нет curl и wget).
  `/readyz` и `/healthz` отвечают без ключа, всё остальное, включая
  `/metrics` самого Qdrant, — только с ключом.
- Каталог служб панели: `qdrant` (группа «Хранилища») — состояние и
  перезапуск.
- `make update` берёт у Qdrant только исправления внутри минорной версии:
  хранилище гарантированно открывается лишь следующей минорной, поэтому
  переход на новую минорную — выпуск этого репозитория, по одной за раз.
- `eva-agent-service` зависит от Qdrant необязательно: без него сервис
  стартует, а поиск работает в degraded.

## Коллекции и версии

Две физические коллекции на версию эмбеддингов:

| Коллекция | Что | Граф HNSW | Индексы payload |
|---|---|---|---|
| `eva_knowledge_private_v<N>` | личные базы | `m=0`, `payload_m=16`: графы по людям | `user_id` (keyword, `is_tenant`), `document_id` |
| `eva_knowledge_global_v<N>` | общая база администратора | `m=16` | `collection_id`, `document_id` |

Приложение ищет через alias `eva_knowledge_private` и `eva_knowledge_global`.
Смена модели — новая пара коллекций, переиндексация в фоне, проверка полноты
и качества, затем перевод обеих alias одним запросом. Прежняя версия
остаётся для отката (тот же перевод alias назад) и удаляется отдельной
командой; активную версию удалить нельзя.

Коллекций на человека нет: личная база — одна коллекция с полем-арендатором.
Шардирование по `user_id` (custom sharding Qdrant) добавляется без смены
формата точек, если одна коллекция перестанет помещаться.

Идентификатор точки — `knowledge_chunks.id`. Повтор записи заменяет точку,
поэтому индексация идемпотентна и возобновляема.

Payload точки — только `chunk_id`, `document_id`, `user_id`,
`collection_id`, `page_start`, `page_end`, `section`, `mime`,
`embedding_model`, `embedding_version`, `created_at`. Текста фрагмента в
Qdrant нет: он читается из PostgreSQL по `chunk_id`. Хранить текст в payload
имеет смысл только после замера, который покажет выигрыш.

## Схема PostgreSQL

Миграции 090 и 091 (K2):

- `knowledge_collections` — коллекции общей базы: код (латиница, уходит в
  payload Qdrant), название, описание, включена ли, порядок. Коллекцию с
  документами удалить нельзя.
- `knowledge_embedding_versions` — версии эмбеддингов: провайдер из реестра
  Router, модель, размерность, мера близости, передавать ли `dimensions`,
  запасной провайдер с моделью, параметры HNSW, состояние
  (`draft → building → ready → active → retired`, либо `failed`). Активная
  одна — уникальный частичный индекс. Провайдера под версией удалить нельзя.
- `knowledge_documents`: `collection_id` (только у общей базы — CHECK),
  `index_status` (`pending`, `indexing`, `ready`, `failed`) и
  `indexed_version` — состояние векторного индекса, отдельное от разбора
  файла (`status`); `chunk_count` для сверки с Qdrant; `revision` и
  `replaces_document_id` — новая версия того же документа; `source`.
- `knowledge_chunks`: `page_start`, `page_end`, `section`, `subsection`,
  `heading`, `token_count`; вектор pgvector необязателен — новые векторы
  живут в Qdrant. Соседние фрагменты — `ordinal ± 1` по уникальному
  `(document_id, ordinal)`: отдельные ссылки previous/next дублировали бы
  его и могли бы разойтись.
- Индексы (091, `CONCURRENTLY`): `to_tsvector('russian', content)` —
  морфология («договор» находит «Договоры»); `gin_trgm_ops` по тексту и по
  названию документа — фамилии, артикулы, обозначения, опечатки.

Проверка на настоящем PostgreSQL — `scripts/ci/test-knowledge-schema.sql`.

## Эмбеддинги через Router

| Имя модели в `/embeddings` | Что считает |
|---|---|
| `eva/embeddings` | прежняя цель: `EVA_EMBEDDING_MODEL`, 1536, вектор pgvector |
| `eva/embeddings@v<N>` | версия N: её провайдер, модель, размерность; при отказе — запасной провайдер той же версии |
| любое другое | отказ 400 `embedding_model_unknown`: опечатка в номере версии не должна давать векторы чужого пространства |

- Провайдеры — из реестра Router (OpenRouter, OpenAI, Gemini, Mistral, Jina,
  Voyage, свой): нужен OpenAI-совместимый `/embeddings`. Ключ и адрес не
  дублируются.
- Отказ провайдера — код (`embedding_auth`, `embedding_rate_limited`,
  `embedding_dimension_mismatch`…) без текста ответа: провайдеры
  возвращают в нём эхо запроса, а это текст документов.
- Не больше 64 текстов за запрос; `LlmRouterClient.embedMany` дробит пачки
  и отвергает неполный ответ и вектор чужой длины.
- «Проверить модель» (`POST /embeddings/probe`) считает вектор
  фиксированной строки: размерность, задержка; с запасным провайдером —
  косинусное сходство векторов (≥ 0,99 — то же пространство).
- Панель: `GET/POST /api/admin/v1/knowledge/embeddings[/probe|/versions]`.
  Версия заводится только после удачной проверки: размерность — из ответа
  модели, запасной провайдер — только того же пространства. Удалить можно
  черновик или неудавшуюся версию; остальные — через смену модели (K7).

## Индексация (K3)

```
загрузка → PostgreSQL: документ, фрагменты (текст, страницы, раздел)
         + задание knowledge_index в job_outbox — одна транзакция
         → COMMIT → BullMQ (очередь memory)
         → векторы пачками через Router (eva/embeddings@v<N>)
         → запись в Qdrant (wait) → снятие лишних точек документа
         → knowledge_documents.index_status = ready
```

- **Нарезка** (`src/knowledge/chunking.ts`): заголовки (markdown `#`,
  «2.1 …», «Глава», «Раздел», строки заглавными) задают раздел и
  подраздел; абзацы собираются во фрагменты не длиннее
  `runtime.knowledge_chunk_size`; фрагмент не пересекает раздел и не
  переходит через страницу посреди абзаца; перекрытие —
  `runtime.knowledge_chunk_overlap`. DOCX и HTML разбираются с заголовками
  (`extractDocumentOutline`), PDF — постранично. Вектор считается по
  тексту с путём заголовков («2. Оплата › 2.1 Штрафы» + абзац).
- **Защита от инъекций.** До нарезки вырезается то, чего человек не
  видит: скрытые элементы, скрипты, стили, формы и комментарии в HTML,
  markdown и тексте, скрытые runs DOCX (`<w:vanish/>`, mammoth их не
  различает). Разбор разметки — однопроходный сканер: незакрытые теги в
  большом файле не дают квадратичного перебора. Типовые формулировки
  команд модели («ignore previous instructions», «run bash…», «enable
  tools…», «забудь прежние инструкции») обезвреживаются без потери
  переносов строк. Конверт «данные, а не инструкции» `knowledge_search`
  надевает при выдаче модели. Известное ограничение: признак `hidden` в
  атрибуте (`class="hidden md:block"`) вырезает и видимое — так было и в
  прежнем санитайзере.
- **Идемпотентность и восстановление.** id точки — id фрагмента; повтор
  задания перезаписывает те же точки и снимает лишние (`pruneDocument`).
  Отказ Qdrant или провайдера — `index_status = failed` с кодом и повтор
  задания; фрагменты в PostgreSQL целы, лексический поиск их находит.
- **Куда.** В каждую версию эмбеддингов со статусом `building`, `ready` или
  `active`: при смене модели новые документы попадают и в индекс, которым
  ищут, и в строящийся.
- **Флаг.** `runtime.knowledge_index_enabled` (`EVA_KNOWLEDGE_INDEX`,
  выключен) и `QDRANT_API_KEY`: без обоих задания не ставятся, а
  поставленные ничего не делают — документ остаётся `pending` до сверки
  (K3b). Прежний вектор pgvector пишется как раньше, пачками: поиск на
  нём, пока его не переключат.
- **Исходные файлы** — том `evaself_knowledge_files`
  (`/data/knowledge-uploads`), в backup входит: это данные людей.
- **Сроки заданий.** Очередь memory по умолчанию даёт заданию 20 секунд —
  документ в сотни страниц за это время не разобрать и не посчитать.
  `knowledge_ingest` — до 10 минут, `knowledge_index` — до 30,
  `knowledge_rebuild` и `knowledge_reconcile` — порция до 25 (K3b).

## Жизненный цикл документа (K3b)

```
загрузка ─┬─ тот же файл (хэш) уже есть у владельца / в коллекции → «дубликат»,
          │  второй документ не заводится, копия файла удаляется
          ├─ новая версия → документ revision+1, replaces_document_id;
          │  прежний снимается после индексации нового
          └─ новый документ
удаление → строки документа, фрагментов и приёма — транзакцией
         + задание knowledge_index: точки во всех версиях и исходный файл
```

- **Кто владелец.** Личная база — человек (`user_id`), общая — никто:
  документ лежит в коллекции (`collection_id`, `product_verified`).
  Загрузка администратора пишет `knowledge_uploads` без владельца, но с
  коллекцией (миграция 092, CHECK: одно из двух). Общие запросы идут в
  системной области с доступом к строкам без владельца (`crossUser`):
  граница не считает `user_id IS NULL` ограничением.
- **Новая версия.** Явная замена (`replaces_document_id` при загрузке)
  или, в общей базе, файл с тем же именем в той же коллекции. В личной
  базе по имени не угадывается: у разных записей бывает одно имя файла
  («voice — расшифровка.docx»), и угадка удалила бы чужую по смыслу
  запись. Векторы неизменённых фрагментов (тот же текст с тем же путём
  заголовков) берутся из точек прежней версии, провайдер считает только
  изменённые. При выключенной индексации прежняя снимается сразу.
- **Исход для человека.** `knowledge_uploads.outcome` (`new`,
  `duplicate`, `new_version`) и `index_status` документа: «новый»,
  «дубликат», «новая версия», «ошибка», «индексируется», «готов».
- **Задание удаления.** `knowledge_index` для документа, которого больше
  нет, снимает его точки во всех версиях, включая выведенную (откат на
  неё не должен вернуть удалённое), и исходный файл, если на него не
  ссылается ни одна загрузка. Ставится и без флага индексации: файл —
  данные человека. Владелец личной базы входит в фильтр удаления.

## Сверка и перестройка (K3b)

`src/knowledge/maintenance.ts`. Оба задания только приводят Qdrant к
PostgreSQL.

- **Сверка** (`knowledge_reconcile`: расписание `job_schedules`, выключено;
  кнопка в панели). По каждой версии `building/ready/active`: коллекции
  нет — перестройка версии; точки чужой `embedding_version` — снять;
  сначала точки Qdrant по документам, потом документы PostgreSQL (в
  обратном порядке документ, заведённый между чтениями, сошёл бы за
  сироту); сироты — снять; документ с числом точек не равным числу
  фрагментов — `pending` и в очередь (кроме того, что индексируется
  сейчас), не больше 500 за проход. Исходный файл без записи приёма
  старше суток удаляется.
- **Перестройка** (`knowledge_rebuild`: «Перестроить индекс», первое
  построение версии, потерянная коллекция). Порции по три минуты с
  курсором по id документа, продолжение — новым заданием: очередь memory
  одна на загрузки и индекс, и перестройка большой базы не держит
  загрузку человека. Документ с полными точками пропускается (полная
  перестройка — `full` — переписывает и его). Новая отметка
  `build_started_at` делает прежние задания перестройки устаревшими. В
  конце черновик становится `ready`; активная остаётся активной — поиск
  на ней не прерывается. Отказ последней попытки: строившаяся с нуля
  версия — `failed` с кодом.
- **Включение версии и смена модели (K7).** Проверка каждого id и payload
  по PostgreSQL, атомарный перевод обоих alias, затем `retired/active`
  одним COMMIT. Протокол, компенсация и откат — в
  [knowledge-operations.md](knowledge-operations.md).

## Панель: общая база (K3b)

`/api/admin/v1/knowledge/…` (`src/admin/knowledge-documents-service.ts`):
коллекции (создать, переименовать, включить, удалить пустую),
документы общей базы (список с фильтрами, удаление, переиндексация по
списку или коллекции), загрузки (очередь с исходом, повтор неудавшейся),
загрузка файла (multipart только на этом маршруте, до 10 МБ; файл — на
общий том, запись приёма и задание разбора — одной транзакцией),
состояние индекса (по личным базам — только числа), построение, включение
версии, сверка. Коллекции и индекс — под `settings:write`. Разбор,
удаление точек и перестройку выполняет агент: публикатор `job_outbox`
читает таблицу, кто бы строку ни записал (`recordJobIntent`).

## Интерфейс (K5a)

**Mini App, вкладка «База знаний»** (`webapp/public/app/knowledge.js`,
маршруты `src/public/knowledge-routes.ts`). Вкладка появляется, только
когда `GET /public/knowledge` отвечает `enabled: true`; при выключенном
`EVA_KNOWLEDGE_UPLOADS` сервиса нет, маршрут отвечает `enabled: false`, и
пятой кнопки в меню нет. Человек видит свои документы и последние
загрузки, загружает файл (`POST /public/knowledge/uploads`, прежний
маршрут), загружает новую версию своего документа (`?replaces=<id>`;
чужой или несуществующий id отклоняется до записи приёма), удаляет
документ (`DELETE /public/knowledge/documents/:id`) и очищает всю базу
(`DELETE /public/knowledge/documents` с телом `{"confirm": true}`) — оба
после подтверждения в интерфейсе. Состояние документа (`ready`,
`indexing`, `failed`) считает сервер: при выключенном индексе Qdrant
разобранный документ готов, потому что поиск идёт по PostgreSQL; коды
ошибок индекса в Mini App не уходят, а причину неудачной загрузки Mini App
называет словами, не кодом. Очистка удаляет документы порциями по 500 и
неудавшиеся загрузки — сначала файл, потом строку приёма: файл, который не
удалился, остаётся найденным для следующей очистки. Файлы и точки
удалённых документов снимает задание `knowledge_index`; задание разбора,
чью загрузку очистка уже сняла, завершается без ошибки.

**Панель, раздел «База знаний»** (`admin-ui/public/ui-knowledge.js`) —
общая база для всех пользователей поверх API K3b: коллекции, загрузка
файлов в выбранную коллекцию (перетаскиванием или выбором, по одному
multipart-запросу на файл; выбор коллекции переживает обновление
раздела), очередь загрузок с исходом, документы со статусом индекса,
порциями по 50 до 200 и массовыми удалением и переиндексацией, состояние
индекса с построением и включением версии и сверкой. Раздел обновляется
сам, только пока идёт разбор, индексация или построение версии; отказ
одного запроса не прячет остальные части раздела. Изменения доступны
ролям owner и admin; читающие роли видят раздел без кнопок изменения.
Личные базы людей в панели — только числа.

## Поиск (K4)

`knowledge_search` — продуктовый инструмент: искать или нет, решает Ева.
Конвейер — `src/knowledge/search.ts`, этапы без базы — `search-fusion.ts`,
SQL — `search-queries.ts`, настройки — `search-settings.ts`.

```
вектор (pgvector или Qdrant, top 30) ┐
FTS russian (top 30)                 ├→ RRF (k=60) → разнообразие → reranker (top 30)
триграммы (top 30)                   ┘   → лучшие 5–10 → соседние фрагменты
                                           в бюджете → источник у каждого
```

- **Режимы** (`runtime.knowledge_search_mode`): `legacy` — прежний поиск
  (FTS `simple` + pgvector одним SQL), умолчание и откат; `hybrid` —
  весь конвейер; `vector` и `lexical` — его половины, для сравнения.
  Переключатель действует со следующего поиска.
- **Источник векторов** (`runtime.knowledge_vector_backend`): `pgvector`
  до K8, `qdrant` — индекс активной версии эмбеддингов. Версия
  называется явно, а не через alias: вектор запроса посчитан моделью этой
  версии (`eva/embeddings@v<N>`), искать им в другом пространстве нельзя.
  Личная коллекция — только с владельцем, общая — только по включённым
  коллекциям.
- **Лексическая половина.** `websearch_to_tsquery('russian', …)` —
  морфология и фразы в кавычках (индекс 091); если строгий запрос пуст
  (длинный вопрос, все слова сразу не встречаются), — любое из слов.
  Оценивается выборка до 2000 совпавших фрагментов: `ts_rank_cd`
  разбирает текст каждой строки, и частое слово на 60 000 фрагментов
  стоило бы секунд. Триграммы (`<%`,
  `word_similarity`, порог 0,5 на транзакцию) — по словам запроса, где
  морфология бессильна: обозначения и артикулы («Р-168-5УН»), номера,
  фамилии; короткий запрос (до трёх слов) — целиком, ради опечаток.
  Слово сравнивается и с текстом фрагмента, и с названием документа:
  фамилия бывает только в имени файла. Это две ветки запроса, каждая на
  своём индексе 091 (одно `OR` по столбцам двух таблиц индексы не
  использует — замер на 30 000 фрагментов: 9 с против 15 мс); документ,
  найденный по названию, представлен одним первым фрагментом. Запрос
  триграмм — отдельный, со своим `statement_timeout` 2 с: частое слово
  совпадает с большой частью базы, и по истечении срока остаются слова
  FTS (`diagnostics.trigram = "timeout"`).
- **RRF** — сумма `1/(60 + позиция)` по спискам: ранги, а не оценки,
  потому что близость вектора и `ts_rank` в разных единицах.
- **Разнообразие.** Одинаковый текст (`content_hash`) — один раз; из
  одного документа — не больше трёх, пока есть кандидаты из других.
- **Reranker** (`runtime.knowledge_rerank_*`): провайдер реестра Router
  (id) и модель с `/rerank` — Jina, Cohere, Voyage, vLLM (формат
  `{model, query, documents}`; Text Embeddings Inference ждёт `texts` и
  напрямую не подходит). Маршрут роутера
  `POST /rerank` (`src/router/rerank.ts`), отказ — код без текста ответа.
  Кандидат для reranker — путь заголовков и текст. Таймаут 4 с; отказ,
  таймаут или незаполненные провайдер с моделью — порядок RRF.
- **Соседние фрагменты** (`runtime.knowledge_context_neighbors`, 0–2):
  `ordinal ± n` того же документа, ближние первыми, без повтора
  перекрытия нарезки и без повтора найденного; дальний — только за
  ближним.
- **Бюджет** — 5000 знаков (до 2000 токенов при 2,5 знака на токен у
  кириллицы, корневой `CLAUDE.md`), источник и раздел каждого фрагмента
  входят в него: найденные целиком, последний укорачивается, соседи — из
  остатка. Не поместившиеся найденные — `omitted_results` в ответе, чтобы
  Ева могла сузить запрос.
- **Источник.** У каждого фрагмента `cite` («Договор.pdf, с. 12–13,
  раздел „2. Оплата › 2.1 Штрафы“»), `pages`, `section`, `base`
  (`personal` или `shared`). Описание инструмента просит Еву называть
  источник, когда она отвечает по документу.
- **Видимость.** Каждый запрос: свои фрагменты, если личная база включена
  (`runtime.knowledge_private_enabled`), и общие — если включена общая
  (`runtime.knowledge_global_enabled`) и коллекция документа не выключена.
  Документ присоединяется с условием владельца: граница арендатора
  (`src/tenancy/`) проверяет каждую пользовательскую таблицу запроса.
  Id из Qdrant — не разрешение: текст читается из PostgreSQL с той же
  видимостью.
- **Отказы.** Нет вектора (провайдер эмбеддингов, Qdrant, индекс не
  включали, коллекции активной версии нет в Qdrant, нет ответа за 8 с) —
  поиск словами, `degraded=true`; векторный режим без
  вектора — те же слова, а не пустота. Отменённый ход не превращается в
  degraded.
- **Выключатель** (`runtime.knowledge_search_enabled`, или обе базы
  выключены): ничего не ищется, инструмент отвечает
  `knowledge_search_disabled`. Документы, фрагменты и точки остаются.
- **Теневой режим** (`runtime.knowledge_search_shadow`): после поиска в
  фоне ищется обоими источниками векторов, в метрики идёт доля
  совпадения первых десяти — ни запроса, ни найденного. Одновременно —
  не больше двух; стоит лишний запрос эмбеддингов на поиск.
- **Что видит модель.** Документ, источник, контекст до и после, текст —
  в конверте «данные, а не инструкции». Оценки этапов (`scores`) и id
  остаются у вызывающего: им место в диагностике панели (K5).

Проверка на настоящем PostgreSQL — `scripts/ci/test-knowledge-search.sql`:
морфология, длинный вопрос, опечатка в фамилии и обозначение через
триграммы, фамилия из названия документа (одним фрагментом),
переключатель личной базы, фрагмент без вектора, чужой документ и

## Изоляция арендаторов

Фильтр строит только `src/knowledge/vector-store.ts`:

  коллекциям; пустой список — пустой ответ, а не поиск по всему.
- Запись проверяет область: у личной точки есть владелец и нет коллекции,
  у общей — наоборот.

## Отказ Qdrant

Отказ Qdrant не роняет разговор. Коды `QdrantError`:

| Код | Что значит | Что делает поиск |
|---|---|---|
| `qdrant_unavailable`, `qdrant_timeout`, `qdrant_server_error` | сбой сервиса (`transient`) | degraded: FTS + pg_trgm, `degraded=true` |
| `qdrant_cancelled` | ход отменён вызывающим | ничего: запрос не уходит, повторять нечего |
| `qdrant_not_found` | alias ещё не создан — индекс не включали; или нет коллекции версии, которую PostgreSQL называет активной (потеряна, не восстановлена) | поиск через alias — пустой векторный результат; поиск по явной версии (K4) — degraded |
| `qdrant_unauthorized` | неверный `QDRANT_API_KEY` | degraded и ошибка в статистике |
| `qdrant_bad_request` | ошибка вызывающего (размерность, фильтр) | ошибка с описанием Qdrant |

Описание отказа Qdrant («Vector dimension error: expected dim: 4, got 3»)
доходит до панели: в нём имена полей и числа, но не ключ и не текст
документов. Текст исключения `fetch` не пересказывается.

  Отдельная внутренняя сеть — меньше прав при той же схеме сегментации.
- **`src/knowledge/qdrant-client.ts`.** Клиента Qdrant в коде нет;
  `@qdrant/js-client-rest` не взят сознательно: нужно полтора десятка
  вызовов, а пакет тянет генерированный клиент всего API. HTTP-вызов с
  таймаутом и кодами — тот же подход, что у клиента Router.
- **`src/knowledge/vector-store.ts`.** Прежний векторный поиск —
  SQL в `src/knowledge/search.ts`, фильтра арендатора для внешнего индекса
  в коде нет. Модуль — единственное место, где строится фильтр Qdrant.
- **`src/knowledge/metrics.ts`.** Повторяет устройство
  `src/tools/tool-metrics.ts` (счётчики модуля, рендер в `MetricsCollector`);
  реестра метрик, куда их можно было бы добавить без нового модуля, нет.
