# Текстовые модели: управляемая маршрутизация

Панель → **Искусственный интеллект**.

Letta не обращается к модели напрямую. Она просит маршрут — `eva/chat`, —
а роутер разворачивает его в цепочку провайдеров. Из-за этого сменить
модель Евы можно, не трогая ни агента, ни контейнеры. Агент Евы остаётся
одним: маршрутизатор выбирает provider для конкретного LLM-вызова, а не
создаёт отдельного агента.

## Режимы

В режиме **Адаптивный** маршрут выбирается детерминированно и без разбора
содержания сообщения: явно запрошенная операция, техническое требование
самого запроса (изображение, строгий JSON), назначение служебного
conversation и явно выбранный человеком баланс качества и стоимости
(`update_llm_quality_mode`). Насколько глубоко разбирать сообщение, какой
навык открыть и нужно ли обращение к памяти, решает Letta — роутер об этом
не догадывается. Пользовательский текст не может подделать route: контекст
от Agent Runtime подписан, проверяется роутером и удаляется до обращения к
внешней модели.

В режиме **Одна модель** выбор маршрута отключён целиком. Все запросы
идут `single_provider_id`. Аварийный переход в прежнюю цепочку `chat` выключен
по умолчанию и, если включён явно, допускается только при сетевой/временной
ошибке, timeout, 429, 5xx или открытом breaker. Сохранённые adaptive-цепочки при
этом не меняются и сразу возвращаются после переключения режима назад.

## Маршруты

| Маршрут | Для чего |
| --- | --- |
| `chat` | Обычный диалог Евы. **Этим маршрутом она и отвечает** |
| `deep` | Разборы целей и режим качества, выбранный человеком |
| `fast` | Фоновые операции и режим экономии, выбранный человеком |
| `research` | Поиск и сопоставление источников |
| `vision` | Анализ изображений |
| `tools` | Запись в NocoDB и Todoist, поиск, работа с памятью |
| `json` | Структурированный вывод для фоновых задач |
| `single` | Технический маршрут выбранной единственной модели |

У маршрута есть требования — инструменты, строгий JSON, поток, размер
контекста, минимальное качество. Модель, которая им не отвечает, в
цепочку не попадает: слабая модель не получит запрос только потому, что
оказалась свободна.

## Цепочка и приоритет

До шести провайдеров: основной и пять резервов. Порядок задают кнопки
↑ ↓ — **порядок и есть приоритет**. Когда основной не отвечает, роутер
берёт следующего, и так до конца цепочки.

Провайдер выпадает из цепочки сам, если:

* выключен или удалён;
* не проходит по требованиям маршрута;
* у него открыт circuit breaker после серии ошибок;
* администратор снял его с автоматического возврата.

Причина видна в разделе — это не молчаливый пропуск.

## Выключатель ротации

**Ротация провайдеров** — переключатель на карточке маршрута.

Выключенная ротация оставляет в работе только основного провайдера.
Цепочка сохраняется, резервы просто не запускаются, и в телеметрии это
называется своим именем — `rotation_disabled`, а не выглядит как «резерв
почему-то не сработал».

Зачем это нужно, лучше всего видно на маршруте `chat`. Резервная модель
отвечает в другом стиле: другая длина фраз, другая манера, другое
качество рассуждений. Пользователь этого не выбирал и не узнает, что
модель подменили. Владелец вправе решить, что молчание честнее подмены,
— и переключатель существует ровно для этого решения.

На остальных маршрутах ротация обычно нужна: фоновой задаче с JSON
безразлично, кто его сформировал, лишь бы формат был соблюдён.

Для распознавания речи устроено так же и теми же словами — см.
[docs/stt.md](stt.md), раздел «Маршрутизация и ротация провайдеров».

## Что при этом остаётся включённым

Выключатель ротации не отменяет:

* **повторы у того же провайдера** — `max_retries` на провайдере, это
  другой механизм: тот же адрес, та же модель, обычно сетевой сбой;
* **circuit breaker** — провайдер с серией ошибок всё равно снимается,
  иначе каждое сообщение упиралось бы в одно и то же;
* **проверку совместимости** — модель без инструментов не получит
  запрос маршрута `tools` ни при каких настройках ротации.

## Тесты

```bash
cd eva-agent-service && npm run build
npx node --test --experimental-strip-types test/llm-router.test.ts
```

Телеметрия `llm_requests` хранит режим, запрошенный и фактический route,
источник/уверенность/score классификации, purpose, correlation ID и фактические
provider/model. Текст запроса, ответа, memory и документы туда не записываются.

API панели: `GET/PUT /api/admin/v1/llm/routing-settings`. Просмотр разрешён
viewer, изменение — owner/admin и попадает в административный audit.

Router держит настройки не более пяти секунд. Успешный PUT публикует
PostgreSQL notification и немедленно инвалидирует snapshot во всех живых
экземплярах router. Если очередное чтение БД временно не удалось,
используется последнее успешно проверенное значение; рестарт не требуется.
