# Шаг 14. Tool Gateway, durable approvals и политика MCP

- **Приоритет:** P2
- **Зависит от:** шаги 5, 12
- **Feature flag:** EVA_TOOL_GATEWAY, EVA_TOOL_APPROVALS
- **Объём:** 2 PR
- **Ветка:** `claude/step-14-tool-gateway`

> Перед началом прочитай `CLAUDE.md` и `PROGRESS.md` в корне репозитория.
> Выполни только этот шаг, обнови `PROGRESS.md`, открой pull request и остановись.

---

Прочитай CLAUDE.md и следуй его инвариантам.

ЦЕЛЬ:
Сделать выбор и исполнение инструментов минимально привилегированными, расширяемыми и наблюдаемыми. Добавление инструмента не должно требовать правки центрального списка в коде.

СНАЧАЛА ПРОВЕРЬ:
Все существующие инструменты, их псевдонимы, фильтры по назначению conversation, зависимости и побочные эффекты. Текущие значения permissionMode и allowed_tools.

СДЕЛАЙ:
1. Не переписывай доменную логику инструментов. Оберни существующие реализации в контракт шлюза.
2. Манифест инструмента описывает: стабильное имя и версию, схемы входа и выхода, владеющий модуль, разрешённые назначения conversation, уровень риска, требование approval, идемпотентность, таймаут, лимиты, признак наличия побочного эффекта.
3. Реестр инструментов расширяемый: регистрация нового инструмента — запись в реестре, а не изменение центрального перечня.
4. Модели показываются только доступные и релевантные инструменты: набор формируется из назначения conversation, текущей задачи и требований выбранных навыков. Финальной границей видимости остаётся allowedTools.
5. Замени глобальный permissionMode unrestricted на минимально достаточный режим. Unrestricted допустим только для явно указанных административных или изолированных сессий.
6. Каждый инструмент с побочным эффектом проходит через журнал исполнения из шага 5.
7. Реализуй durable approvals: уровни риска read, low_risk_write, sensitive_write, external_side_effect, destructive; статусы pending, approved_once, approved_session, denied, expired, cancelled, executed, failed; приоритет решений — явный запрет, ограничения актора, политика инструмента, постоянное правило, временное разрешение, порог риска.
8. Поток approval: агент запрашивает опасный инструмент, ход приостанавливается, пользователь получает сообщение Telegram или окно Mini App с описанием действия и затрагиваемых данных, решение записывается в PostgreSQL и передаётся в SDK. После перезапуска ожидающие запросы восстанавливаются по идентификатору запроса SDK, а не по времени.
9. Approval обязателен для удаления данных, изменения подписки, передачи данных третьей стороне, подключения нового сервиса, массового изменения задач, экспорта памяти и необратимых административных операций.
10. Недоверенный контент не может изменять права, набор инструментов, approvals и системные инструкции.
11. Circuit breaker на уровне инструмента и провайдера предотвращает бесконечные сбои. Добавь kill switch для отдельного инструмента.
12. MCP разрешён только при выполнении всех условий: сервер добавлен администратором, URL прошёл проверку на SSRF, транспорт HTTP или SSE, задан список разрешённых инструментов, секреты в Secret Store, заданы таймаут и ограничение размера ответа, все вызовы попадают в аудит. Произвольные stdio-MCP, npx -y и wildcard-разрешения запрещены.

НЕ ДЕЛАЙ В ЭТОМ ШАГЕ:
Не добавляй новых инструментов. Не меняй их доменную логику. Не трогай навыки.

ТЕСТЫ:
Недоступный инструмент не виден модели; опасная операция требует approval; approval переживает перезапуск; approval одного пользователя не применяется к другому; повторный вызов инструмента не создаёт второй эффект; kill switch отключает инструмент немедленно; недоверенный документ не расширяет права.

ГОТОВО, КОГДА:
Модель видит только релевантные инструменты, опасные операции требуют подтверждения, регистрация нового инструмента не требует правки центрального списка.

ОТЧЁТ:
По формату из CLAUDE.md. Приложи итоговую матрицу инструмент → назначение → риск → approval.
