Прочитай CLAUDE.md и следуй его инвариантам.

ЦЕЛЬ:
Диагностировать состояние памяти и формировать проверяемые отчёты, не изменяя критические данные напрямую.

СНАЧАЛА ПРОВЕРЬ:
Модель памяти после шагов 15 и 16 и конвейер кандидатов.

СДЕЛАЙ:
1. Реализуй фоновый диагностический сервис, выполняющийся как agent job с ограниченным бюджетом.
2. Проверки: дубликаты, семантически одинаковые записи, противоречия, устаревшие факты, неверная версия по времени, слишком низкая уверенность, отсутствие доказательств, неактуальные цели, избыточный объём основной памяти, факты с неверным режимом приватности, потерянные связи графа, осиротевшие embeddings, расхождение между PostgreSQL и блоками Letta.
3. Отчёт содержит разделы по каждому типу проблемы и список предложенных действий. Каждая проблема содержит ссылки на конкретные записи и доказательство, а не общую формулировку.
4. Memory Doctor не изменяет данные напрямую. Все предложения проходят через тот же конвейер кандидатов, что и Curator.
5. Триггеры: ручной запуск администратором, запуск пользователем из Mini App, значительный рост объёма памяти, обнаруженное противоречие, смена версии схемы памяти, плановый низкоприоритетный запуск, перед экспортом памяти, после переноса данных. После каждого сообщения не запускается.
6. Применение предложений — только явным действием администратора или пользователя, с предпросмотром, diff и откатом.

НЕ ДЕЛАЙ В ЭТОМ ШАГЕ:
Не давай сервису право прямой записи. Не запускай его в пути ответа. Не изменяй блоки persona и human автоматически.

ТЕСТЫ:
На подготовленном наборе с известными дефектами отчёт находит все внесённые проблемы и не выдаёт ложных; применение предложения проходит через кандидатов; откат восстанавливает прежнее состояние; отчёт не содержит сырого пользовательского текста сверх необходимого доказательства.

ГОТОВО, КОГДА:
Отчёт воспроизводим и проверяем, ни одна проблема не исправляется автоматически без действия человека.

ОТЧЁТ:
По формату из CLAUDE.md. Приложи пример отчёта на тестовом наборе.
